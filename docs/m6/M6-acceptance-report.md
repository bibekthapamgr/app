# M6 — DNS, TLS and traffic routing: acceptance report

**Status: every M6 acceptance criterion passes in CI on four Android versions (API 29, 34, 35 and 36), in three runs of the same commit, after four independent reviews whose findings were all fixed. A fact-check of this report then found that the checks of other apps' traffic while connected leave out each period's first and last 2 s, so they covered only 4 to 6 of the 40 periods per level, about half the connected time, and a measurement after it found the emulator's own capture lined up about a second wrong on API 34 and 36; the report now states both and what those moments hold, and hands the evidence fixes to M8 (Decisions). Awaiting the product owner's review of pull request #5; ADR-0011 was accepted under the owner's delegation and can be reopened. Decisions D2, D6 and D7 stay with the owner.**

The workspace this was written in cannot reach Google's Maven repository, emulators or Actions artifacts, so everything Android ran in GitHub Actions. Locally: the engine's Go tests (with the race detector), the evidence scripts' tests on synthetic captures, `core/vpn`'s 61 tests (the session and the diagnostics mapping) and `CopyClaimsTest` compiled with kotlinc against stubs, ktlint on every Kotlin change, and the secrets scan on the final tree; CI runs all of them again on every push. CI reports test counts, the end-to-end evidence and every failure as annotations readable through the GitHub API.

The owner delegated the networking decisions ("Timi nai decide gara"); ADR-0011 was accepted on that basis. **D2** (plaintext proxies in the Play build), **D7** (TLS default in the form) and **D6** (what "Test connection" contacts) stay open from M4 and M5. None of them blocks M7.

What goes through the VPN is unchanged from M1, M4 and M5, and now measured on devices: TCP (IPv4 and IPv6) goes through the proxy, by name where the app asked by name; DNS is answered on the phone with placeholder addresses (over UDP and, since M6, over TCP) so that the proxy resolves names; UDP other than DNS is refused with "port unreachable"; pings are never answered; nothing falls back to a direct connection or a direct lookup when the proxy fails. Android itself decides what never enters any VPN: ProxyFlow's own connection to its proxy, some of Android's own traffic and that of privileged preinstalled apps (seen on Android 15: Google Play services' connections, its push messages included), other profiles and users, tethered devices. The full matrix with each row's device test is `docs/m6/routing-and-limitations.md` §1.

## Acceptance criteria

| Criterion (brief) | Evidence | Result |
|---|---|---|
| Packet captures confirm supported TCP traffic uses the configured proxy | The device tests send lines from the shell (covered by the VPN) to destinations where a path around the proxy would show: by name (`proxyflow.test`, a name only the proxies' DNS server knows), by IPv4 address (`10.99.0.2`) and by IPv6 address (`fd99::1`) (the emulator's network would carry a direct connection to these, and it would show in the captures and in the destination's log), to a name with only an IPv6 address (`proxyflow6.test`) and to the LAN address (`10.0.2.2:8082`, where the phone's own path lands on the runner's loopback with nothing listening), each through SOCKS5 and HTTP CONNECT, and get each destination's answer. `scripts/m6_evidence.py` then matches every line against the destinations' logs (each arrived exactly once), each destination's connections against the tunnels Squid and Dante opened to it (equal: nothing arrived around a proxy), and reads the captures of the phone's uplink from start to end: the phone's SOCKS5 and HTTP CONNECT requests to its proxies (the lab's names asked for by name), no packet to or from any destination's address, no SYN straight to the LAN destination. M5's checks (`m5_evidence.py`) hold on the same runs. The evidence also checks other apps' traffic while ProxyFlow was connected, in each period but its first and last 2 s (about half the connected time, as most periods are short: End-to-end evidence): there no new connection, datagram or ping left the phone on its own network other than to its proxy, its network's resolver and Android's own network and time checks — or traffic of apps Android lets leave a VPN: on API 35 over Wi-Fi, in attempts 2 and 3, Google Play services' connections (to ports 5228 and 443 of placeholder addresses), named by the phone's socket table as owned by an app granted `CONNECTIVITY_USE_RESTRICTED_NETWORKS`, and reported. In the parts left out, measured afterwards with the same owner rules, the phone's own captures hold expected traffic, Google Play services and Android's network stack and a few connections with no owner sampled, and no ordinary app's traffic (End-to-end evidence). Android's own view of the VPN, logged after each of the 39 connections the tests made through their helper, routed every uid but ProxyFlow's (and, on API 34 to 36, its SDK sandbox's) into it and, where Android says (API 34 to 36), let no app bypass it; ProxyFlow's own sockets reached nothing but its proxies and the gate's control port. The limitation is documented (routing doc §4, About, README, ADR-0011). Figures per API level: End-to-end evidence below | **Pass** |
| No silent direct DNS fallback occurs | DNS over UDP and over TCP port 53 is answered on the phone whatever server an app asks: the same placeholder from the VPN's 198.18.0.2, the network's own resolver 10.0.2.3 and 8.8.8.8 over UDP, and from 198.18.0.2 and 8.8.8.8 over TCP (`namesAreAnsweredOnThePhoneAndResolvedByTheProxy`; DNS over TCP was proxied before M6, ADR-0011 §1). DNS an app encrypts itself (over TLS or HTTPS) goes through the proxy as ordinary TCP (routing doc §1). The lab's names are looked up only at the proxies' DNS server (dnsmasq 10.99.0.53, which logged queries for `proxyflow.test`, `proxyflow6.test`, `secure.proxyflow.test` and `missing.proxyflow.test`, a name that does not exist); the phone's uplink DNS server (10.99.0.54, the emulator's `-dns-server`) was never asked for one of them, and no capture of the uplink holds a DNS query for one, from start to end — also while the proxy refused (`whenTheProxyStopsAnsweringNothingGoesAroundIt`), hung (`aProxyThatHangsIsReportedAsATimeout`) or could not resolve the name (`aNameTheProxyCannotResolveFailsWithoutAFallback`, which also checks Home counts it as a DNS problem). The only name the app looks up itself is the proxy's own, logged by the uplink server (`theProxysOwnNameIsLookedUpByTheApp`), and an unknown proxy name never connects (`PROXY_DNS_FAILED`). In the checked parts of the connected periods the uplink DNS server's log and every covering capture hold no lookup on any level, not even of the proxy's name; in the parts left out, the phone's captures hold the app's own lookups of its proxy's name (it looks the name up when it connects or switches proxy) and one of Android's check names, sent to the network's resolver, and Google Play services' lookups addressed to the VPN's DNS address 198.18.0.2, which nothing there answers. Right after disconnects, other apps' lookups addressed to 198.18.0.2 cross the phone's network too, names in clear (End-to-end evidence) | **Pass** |
| TLS certificate validation cannot be bypassed automatically | TLS to the proxy works with a certificate the phone trusts (`httpConnectOverTlsCarriesTraffic`, `socks5OverTlsCarriesTraffic`: the platform's trust manager with the run's CA as its one anchor, ADR-0011 §6) and fails, never Connected, never an interface, with a certificate for another name (`TLS_HOSTNAME`), an expired one (`TLS_EXPIRED`), one from another CA (`TLS_UNTRUSTED`), the app as shipped facing the run's CA (`TLS_UNTRUSTED`) and a proxy without TLS on the port (`TLS_HANDSHAKE`). While connected, a proxy whose certificate changes to an untrusted one gets each new connection refused, Home names the check, and traffic resumes once the valid certificate is back (`aCertificateThatChangesWhileConnectedIsRefusedForEachConnection`). Home, which shows a refused certificate, offers no way around it (`HomeScreenTest.aRefusedCertificateOffersNoWayAroundTheCheck`), and a profile has no setting that accepts an untrusted certificate (TLS on or off and the name to check). In the captures and at the gate, every connection to a TLS proxy port opened with a TLS record: nothing was retried in plaintext; the TLS fronts logged the handshakes the app ended with a "bad certificate" alert | **Pass** |
| Unsupported traffic follows documented fail-closed/error behavior | UDP (IPv4 and IPv6) to the lab's sinks gets "port unreachable" at once from ProxyFlow, the engine counts it by port and Home counts it as unsupported traffic; the sinks received nothing and no capture shows UDP to them (`udpIsRefusedOnThePhoneAndNeverSent`). `ping` and `ping6` get no reply, the engine dropped the requests and sent no reply, Home counts them, and no capture shows an echo request leaving the phone for a destination (`pingsAreNeverAnswered`). Proxy failures while connected (refusing, hanging, an untrusted certificate, a name it cannot resolve) end each connection on the phone and stay Connected with traffic held, as `docs/m6/routing-and-limitations.md` §2 documents | **Pass** |
| HTTPS destination TLS remains end-to-end and is not intercepted | `httpsToASiteStaysEndToEnd`: through a plain SOCKS5 proxy and through HTTP CONNECT over TLS, the shell's TLS client (trusting only the run's CA and checking the name as browsers do) completed TLS with `secure.proxyflow.test` and saw the site's own certificate — its SHA-256 equals the one the runner made for the site; the HTTPS site logged only sessions for the name the client sent. ProxyFlow relays the bytes; it holds no certificate it could present in the site's place | **Pass** |
| User-facing copy does not claim universal traffic coverage or anonymity | `CopyClaimsTest` reads every string of every module (and any translation) and fails on universal coverage ("all traffic", "every app", "full VPN"), anonymity or hiding identity (except About's sentence denying it), blanket security ("100 %", "military-grade", "protection"), "no logs", or support for UDP, games or calls; it requires the limitation texts (About: not anonymous, UDP blocked, IPv6, what doesn't use the VPN — work profiles, other users and tethered devices required; About's sentence also names ProxyFlow's own connection and lookup, some traffic of Android and its built-in apps such as Google Play services, and Private space, which `AboutScreenTest` checks in part — TLS versus HTTPS; Home's notes; the form's TLS hint and plaintext warning; the notification) and bans the ambiguous "encrypted"/"TLS" alone for the TLS setting. The setting reads "TLS to proxy" on Home and the profile chips and "TLS to the proxy" in the form and About; Home, the form and About each say that HTTPS sites stay encrypted end to end. Screenshots of every screen are in `app/screenshots`, in both themes except seven in the light theme only (B6, B9, C2, C3, D8, E1, H1) | **Pass** |

## Independent reviews

Two reviewers who had not written the code reviewed the whole milestone at the same time, with different briefs: one the whole diff (at `f4bbdff`), one adversarially, looking for ways the guarantees could fail while the tests and evidence still pass (at `a9f122d`). Neither found a path for traffic or DNS to leak, a TLS check that can be skipped, or a way for the shipped app to use another trust manager. Their findings were about the evidence's blind spots and about claims the code did not back; all were fixed in `bc4f219` and `e348a67`. A third reviewer then checked those fixes (`a9f122d..242bf88`): ten of the thirteen complete, three partly, and new gaps in the new checks themselves, all fixed in `843d916` and `dd3aa11`. ## Decisions, deviations and open items

- **ADR-0011 accepted under the owner's delegation** ("Timi nai decide gara"): DNS over TCP answered on the phone, ProxyFlow's own addresses refused locally, no fallback anywhere, IPv6 by address with IPv4-only placeholders, TLS to the proxy unchanged from ADR-0005, the test-only trust seam, diagnostics, copy rules and the verification lab. It can be reopened.
- **Owner decisions still open:** D2 (plaintext proxies in the Play build) and D7 (TLS default in the form), both ADR-0005; D6 (what "Test connection" contacts, and the pre-flight target the privacy policy must name). None blocks M7.
- **A trust seam in shipped code.** The device tests need TLS to the proxy to succeed with a certificate from the run's own CA, which no phone trusts. `AppContainer`, `VpnRuntime` and `ProxyTunnelEngine` therefore take the TLS proxies' trust manager as a constructor parameter; only the instrumentation (`E2eTestRunner`, in the test APK) passes one — the platform's own implementation with the run's CA as its one anchor. The app as installed has no way to set it (no setting, intent, file or network input; `ProxyFlowApplication` uses the default), and `theAppAsShippedTrustsNoPrivateCa` shows the default refuses the run's CA on every API level (ADR-0011 §6).
- **What is measured on emulators, not phones.** As in M5: physical phones and vendor builds come with M10. Android Private DNS in strict mode is not automated (it needs a DNS-over-TLS server with a publicly trusted certificate); its behaviour follows from the TCP rows and is on the M10 checklist. Private DNS "Automatic" (the default) runs in every device test.
- **What M6 does not do, by plan:** following network changes, reconnecting and the escalation rule for a proxy that keeps failing while connected (M7: until then Home stays Connected and counts the failures, which are refused connection by connection, never sent around the proxy); traffic counters and the session log (M7, on the same counters); kill-switch guidance (M8).
- **Android lets privileged system apps bypass the VPN.** On API 35 over Wi-Fi, Google Play services opened TCP connections to ports 443 and 5228 (its push messages) outside the VPN a few seconds into some connected periods, in runs from 41270141033 on (the first whose captures the connected-period checks could line up), though not in every attempt: in the verified run, 3 in attempt 2, 2 in attempt 3 and none in attempt 1. From run 41272331602 on, the phone's socket table named their owner (`com.google.android.gms`: uid 10143; in attempt 3 of the verified run, uid 10144). There they went to placeholder addresses from ProxyFlow's DNS and could not connect; on a phone such connections could reach Google directly. On API 36 the captures showed connections around the VPN that no socket sample caught in two earlier runs (41274352491: to Google's push servers, with lookups of their names; 41277623353: to port 80 of a Google address), none in the verified run; no other level showed any. Both were seen only in the emulator's own capture, which the evidence can line up about a second wrong (the next point), so they may have fallen just outside a period. ProxyFlow cannot prevent it: Android grants this to privileged apps whatever the VPN does (Google answered Mullvad's 2022 report that Android's own connectivity checks leave a VPN, even with "Block connections without VPN", as intended behaviour: [Mullvad](https://mullvad.net/en/blog/android-leaks-connectivity-check-traffic)). ProxyFlow never calls `allowBypass()`, so ordinary apps cannot leave the VPN — the tests' own traffic, from the shell, never did on any level. Documented in About, the README, the routing doc §4, ADR-0011, the traffic matrix and the threat model (R5). The evidence reports what system uids and apps with a network bypass permission own, fails on any other owner, and puts what no socket sample caught down to such apps only when Android's own view of the VPN routed every uid but ProxyFlow's into it and ProxyFlow's own sockets reached nothing but its proxies and the gate's control port.
- **The checks of other apps' traffic while connected covered 4 to 6 of the 40 periods per level, about half the connected time, and the emulator's capture was lined up about a second wrong.** The first version of this report (`b0d134e`) said every period was checked. A fact-check against the evidence found the margins; measurements afterwards on the artifacts GitHub keeps (attempt 3's), with the evidence script's own functions in one-off Actions jobs, gave the coverage, what the moments left out hold and the emulator capture's real offset (End-to-end evidence). In those moments the phone's own captures hold only expected traffic, Google Play services and Android's network stack and a few connections with no owner sampled — no ordinary app's traffic. Right after disconnects, apps' DNS queries addressed to the VPN's DNS address go out on the normal network: no answer, but the names in clear. No verdict above rests on these checks: each criterion rests on the tests' own traffic and on checks over whole captures and logs. For M8 (kill switch and hardening): check the moments around connecting and disconnecting with their senders named (the classification used here), line the emulator's capture up by the phone's own capture where both exist, report checked time in the evidence, log Android's view of the VPN for every connection the tests make (the consent test and the repeated-starts test log none), re-check the two earlier API 36 findings (below) against the phone's capture, and find out whether the DNS queries to the VPN's DNS address after a disconnect can be avoided. The routing doc §4 states the limitation.
- **Diagnostics are counts.** No destination, name or address is shown or stored, and only while Connected. The last problem shows the engine's code and its fixed detail text, which never contains a destination.
- **Captures.** As in M5: API 29 has only the emulator's own capture; API 34 and 36 have it and tcpdump on the phone's uplink interface; API 35 (Wi-Fi inside airplane mode) has only the phone's tcpdump. The plaintext profiles' captures hold the run's random sign-ins by design; the captures stay in the run's artifacts.
- **The lab is on the CI runner.** The emulator reaches it as `10.0.2.2`; destinations sit on addresses (`10.99.0.0/24`, `fd99::/64`) that are not on the phone's network, so any packet the phone sent to one directly would show in the captures, and the phone's uplink DNS server knows only the proxy's name, so a direct lookup would show in its log. A capture that saw no app connection to both proxies does not count as covering the uplink.
