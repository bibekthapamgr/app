# ADR-0017 — Launch and maintenance: the support process, the scheduled reviews, the locks that keep the policy true, and the release discipline after V1 (M12)

**Status:** Technical decisions accepted 2026-11-08 (delegated by the owner, "Timi nai decide gara"; implemented in M12); the owner's part is the calendar of `docs/m12/maintenance-runbook.md` · **Date:** 2026-11-08

## Context

M12 asks for the app to be maintained safely after release: privacy-respecting crash and error signals and user feedback; a support and bug-report process that tells users not to share proxy passwords; triage of compatibility, connection and security bugs; dependencies and the target API updated as required; regression tests for protocol and routing kept; staged rollouts and a rollback procedure; a changelog, release notes and an incident-response runbook; the privacy policy and the Play declarations reviewed whenever the data behaviour changes. Its acceptance: every release with a changelog and regression results; critical security reports with a named owner and a process; profile data compatible or safely migrated; rollback and incident instructions; policy and dependency reviews scheduled.

The project has one maintainer, no servers, no SDK that reports anything, and a privacy policy that says "nothing to the developer" (ADR-0016 §6). Whatever maintenance adds must keep that true, and must run without anyone remembering to run it.

## Decision

1. **No signal of ProxyFlow's own; Google's, under the user's setting, is the only crash signal** (`docs/m12/support.md` §1). Android vitals (crashes, ANRs, the crash-free rate), Play reviews, the support e-mail, GitHub issues and GitHub's private vulnerability reporting are the channels; no crash SDK, analytics or in-app feedback form is added, so the Data safety answer "no collection" stays true and the data-behaviour lock (decision 5) would fail a build that added one.
2. **Users are told, everywhere they could write to the developer, never to send a proxy password** (`support.md` §2): the issue template (a required checkbox and a bold warning), the mailbox's auto-reply, the listing's support text and the app's own Help → Feedback (`help_feedback_body`, guarded by `CopyClaimsTest`). What slips through is redacted with `scripts/release/redact_report.py` before it is kept, and the reporter told to change the password. The exported log is what users are asked for, since it already carries no credential, server or site (M7).
3. **A named owner, a second person, and a clock for security reports** (`SECURITY.md`; `docs/m12/incident-response.md`; `docs/m12/maintenance-runbook.md` §1.1): the repository owner; acknowledgement in 3 days, assessment in 7, a fixed release for a critical finding on the internal track in 14 days, high in 30; disclosure after the fix has reached everyone. Severity is defined by what the app promises (a leak around the proxy, a credential exposed, the kill switch failing, a crash a remote peer can cause are critical — the same list in `SECURITY.md` and the runbook). A single owner cannot keep a clock alone, so a second person holds a Play Console user with the release and policy permissions, a key backup, repository admin and the mailbox, named in the release checklist's sign-off. GitHub's private vulnerability reporting is a repository setting the checklist turns on. The process is drilled once before production and yearly, the halt on the closed-testing track (the internal track has no staged rollout).
4. **Triage by kind, with the first question written down** (`docs/m12/triage.md`): security, routing, connection, protocol compatibility, device compatibility, crash, UI, question; a documented limit is answered with the document and counted, so that the limits users hit most shape the next help text; a provider-specific protocol deviation is reproduced in the lab with the host redacted, never with the reporter's credentials.
5. **The data behaviour is locked** (`scripts/check_data_behavior.py`, `docs/m12/data-behavior.lock`): a fingerprint of the manifests' permissions, services and `<application>` attributes with the backup and network-security XML, the connectivity-check destination, the Room schemas, the DataStore keys, the log's retention, what the log may hold and what its export shares (`Logs.kt`), the `privacy_*` strings, the policy document without its version line (so a version bump alone does not break the lock and `--update` stays a reviewed act, not a rote step), the declarations document, the version catalog's tables and the dependency review; CI fails on every push and pull request when any of them changed since the last review — in the `android` build, and in `pages.yml` for a commit that touches only documents, which `android.yml` ignores — until the review of `docs/m12/policy-review.md` is done and the lock rewritten with the reviewer and the note. A quarterly review happens whether or not anything changed, because Google's forms move.
6. **Dependencies by dependabot, the platform by hand, vulnerabilities on a clock** (`.github/dependabot.yml`, `docs/m12/maintenance-runbook.md` §3): monthly grouped pull requests that the whole CI runs on; the Android Gradle plugin, Kotlin, Gradle, Go, gomobile and the NDK yearly on a branch of their own with three green runs; OSV at today's resolved versions monthly (`.github/workflows/maintenance.yml`), a reachable vulnerability handled as an incident.
7. **The target API is watched by a script with Google's dates** (`scripts/check_target_api.py`, `docs/m12/play-target-api.json`): a passed requirement fails every build (a warning instead, until the extension date, only when the owner says Google granted the extension: `--extended`), one within 120 days warns, a rules file older than 180 days warns, an `expected_next` that the rules already list is flagged so the next year's lead is kept; the bump is a procedure of the runbook with a month's lead.
8. **A release is a version everywhere at once, refused until its documents exist** (`scripts/release/bump_version.py`, `scripts/release/check_release_ready.py`, `CHANGELOG.md`, `docs/m12/release-history.md`): one command bumps the version code and name, opens the changelog section ("release candidate"), adds the history row and regenerates the privacy policy's version line; CI refuses a tree whose version has no changelog section or history row, whose policy names another version, or whose data behaviour is unreviewed; `--release-run` (before the hand-started release run) refuses a row without the verified commit and its green `android` run and a non-empty `[Unreleased]`; `--production` (before the upload) refuses a pending `release` run and a heading neither dated nor marked "release candidate" — the production date is a docs-only commit after the rollout, because the tagged commit cannot carry a date that is not yet known. Version names are always `MAJOR.MINOR.PATCH` and forward, a rollback included. The history row is where the regression results (the runs' ids) and the crash rate of each release live; 1.0.0 (11)'s row is filled from M12's verified commit, since M12 changed the app's Help text after M11's.
9. **Staged rollouts with fixed gates; a rollback is a forward release that may need a downgrade migration** (`docs/m12/rollback.md`): 5 % → 20 % → 50 % → 100 % on 2–3-day holds gated on Android vitals' crash rate (0.2 % of daily active users; the user-perceived rate under Google's threshold), new clusters and reports, with a rule for the days vitals show no figure; a halt within the hour for a critical finding, and 100 % at once for the rollback of a critical release, since a halt leaves the users who have the bad release on it; the rollback is made on a branch from `main` by restoring the good tag's code file for file (`git checkout <tag> -- app core engine feature`, never `git revert`, which would take the records back too) while keeping its version bookkeeping and every document (Play has that code for good; `bump_version.py` counts above every row of the history), with a normal forward version name (the tooling accepts nothing else) and the three runs on the merge commit on `main`, which is the verified commit every release's row names and its tag marks. When the bad release bumped the profiles' Room schema, a downgrade migration that recreates the table with exactly the old columns (Room validates columns on open; `DROP COLUMN` needs SQLite 3.35, which Android 10–13 lack), with a test from the newer schema's exported JSON, because Room refuses a newer database and the profiles would otherwise be unreadable; a destructive migration is forbidden on the profiles database in both directions, by test and by a CI grep. The ephemeral log database is the one exception: `LogDatabase.create` drops a newer `logs.db` on downgrade (`fallbackToDestructiveMigrationOnDowngrade(true)`, with a test), so the Logs screen opens after a rollback. The credentials' sealed format is versioned (ADR-0006) and reports itself unreadable across a bump, so the profile stays and the sign-in is re-entered.
10. **The monthly review is an issue the workflow opens** (`.github/workflows/maintenance.yml`): the checks' results in its first line and the owner's checklist as tick boxes — vitals, reviews, mail, dependabot, OSV, the target API, the Play Console inbox, the quarterly policy review, the last release's open columns — so the calendar of `maintenance-runbook.md` §2 has a place to be ticked and a history.

## Alternatives considered

- **A crash-reporting SDK** (Firebase Crashlytics, Sentry): better traces, faster alerts; but a third party receiving device data from every user, a Data safety answer that is no longer "no collection", and a policy that would have to say so. Android vitals gives the crash-free rate and sanitized traces under the user's own setting.
- **An in-app feedback form**: a destination of ProxyFlow's own, which the app has none of; the exported log plus a mail or an issue does the same with the user holding the data.
- **Pinning dependencies and never updating**: no churn, but no vulnerability fixes; the monthly OSV check against the *resolved* versions is the compromise.
- **A lock on the whole source tree**: every commit would be a "data behaviour change"; the ten items are the ones that decide what is kept or sent, and the dependency review catches a new library.
- **Trusting the migration tests for rollback**: they prove forward migrations and that a newer database is not destroyed; the rollback document has to say the rest, and does.
- **A `-rN` version suffix for rollbacks**: honest about what the release is, but every script (`bump_version.py`, `check_release_ready.py`, the policy's version line, the changelog links) would need to learn it, with tests, exactly when time matters; a forward name with the changelog saying "re-releases 1.0.0's code" costs nothing.
- **A destructive downgrade for the profiles database too**: one line, and no rollback could ever strand a user at a crash; but it would delete every profile and credential on the phone of a user who got a rollback, the one thing the app promises to keep.

## Consequences

- One person's calendar is in a workflow and a document; a second maintainer could follow it.
- A change to what the app keeps or sends cannot ship by accident; it costs a review and a note.
- Every release carries its changelog section, its history row and its runs' ids, or CI refuses it.
- Users are told the one thing that matters at every door, and the owner has a script for what they send anyway.
- The policy, the forms and the target API are re-read on a schedule a script enforces, not a memory.
