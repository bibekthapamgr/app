# ADR-0016 — Google Play release: signing, the release workflow, the proof a signed bundle works, the listing and the declarations (M11)

**Status:** Technical decisions accepted 2026-11-07 (delegated by the owner, "Timi nai decide gara"; implemented in M11); the owner's decisions D2 (plaintext proxies in the Play build) and D10 (name, package, support contact, Play account, testers) open · **Date:** 2026-11-07

## Context

M11 asks for a compliant, signed Android App Bundle submitted through the right Play process: the account's status and testing requirements confirmed; name, package, icon, screenshots, descriptions and support contact final; a public privacy policy that reflects the app; Data safety, app content and VpnService declarations with prominent disclosure; the target API verified at submission; release signing configured securely with no key or password ever committed; the signed bundle built and tested on clean devices; internal and closed testing; and a listing that promises no unsupported UDP, anonymity or guaranteed coverage. Its acceptance: the signed bundle installs and runs; declarations match the app; the account's testing requirements are met; keys stored securely and backed up; store assets and privacy policy live and reviewed; submission only after checklist sign-off.

What M10 left: the release build and bundle unsigned; the Roborazzi screenshots at a ratio Play refuses; the privacy policy a document in the repository; the Play facts unverified; and the owner's Play account, name, contact and testers unknown to the project.

## Decision

1. **The upload key is the owner's, made outside the repository, and the only key the project ever holds** (`scripts/release/make_upload_key.sh`, `docs/m11/signing.md`). Play App Signing keeps the app signing key with Google (generated there); the upload key is made on the owner's computer by a script that refuses a checkout and an existing keystore, asks the password silently, and prints the certificate's SHA-256 and the next steps. It lives in two offline backups and, base64-encoded, in three GitHub Actions secrets that only a run the owner starts by hand is handed; `.gitignore`, the secrets scan (by name and by content) and the script's refusals keep it out of the repository. Gradle reads the signing configuration from the environment or an untracked file and otherwise builds unsigned: there is no default.
2. **One release workflow signs, verifies and proves the bundle on every push with a key of the run, and with the upload key only when the owner starts it by hand** (`.github/workflows/release.yml`). The engine job is shared with `android.yml` as a reusable workflow (`engine.yml`). The bundle job is handed the secrets only on `workflow_dispatch` on `main` — a push's or pull request's run, and a hand-started run of any other branch, signs with a run key (30 days, "not for distribution"), so no branch's build scripts but `main`'s ever run with the upload key in their environment —, decodes the upload key into `$RUNNER_TEMP` or makes the run key, checks the keystore opens and the alias exists, reads the certificate's fingerprint and requires the hand-started run's `fingerprint` input to equal it — a bundle signed with any key but the one Play knows fails here, not at upload —, builds `bundleRelease` and `assembleRelease` with the four values in the environment of that step (and of bundletool's, which signs the APK set) and no other, reads the version back from the APK, verifies the bundle's jar signature and that its one signature block's certificate is the key's (`openssl pkcs7`), verifies the APK has one signer with the key's certificate (`apksigner`), runs M8's release checks on the same build, and with Google's bundletool (pinned by version and SHA-256) validates the bundle and builds the full APK set and the universal APK, all attached with `release-facts.txt` (mode, fingerprint, version, event, ref, commit, run, bundletool's hash, the native ABIs, the bundle's SHA-256). The key file, its environment file and the password files are removed at the end of the job whatever happened; no password is printed or put on a command line (GitHub masks the secrets, `::add-mask::` the run key's; keytool reads them from the environment, bundletool from a file). The mode is in the notices of the key, the version, the signatures, bundletool and the bundle and in the artifact's name; the event and the ref in the facts and in the key's and the bundle's notices — so neither a run-key bundle nor an upload-key bundle of another run can be mistaken for the one to upload.
3. **The proof is the signed bundle installed the way Play installs it and used through the app's own screens** (`scripts/m11_signed_smoke.sh`, `scripts/release/ui.py`). On fresh API 29 and API 36 emulators (a phone's screen) with the M5–M10 lab: bundletool `install-apks` picks the device's split APKs from the signed set; the package installed must be the application id, and the installed app's certificate (pulled `base.apk`, `apksigner`), debuggable flag, version name and code are checked against the bundle job's; then, with uiautomator and no test hook — the release build has none — onboarding, Add proxy with the lab's SOCKS5 proxy and sign-in, Save, Connect, the app's own VPN explainer, Android's consent, Connected; one line from the shell client to a destination reachable only through a proxy must come back; the witness must be refused; Disconnect must show Not connected; since the lab came up, the destination's connections must equal Dante's tunnels to it (one and one), the witness's log have no new line, the uplink resolver no lookup of the destination's name. A step that fails stops the flow with the screen's evidence; the device is cleaned whatever happened. The screen is recorded for Play's declarations. A build that installs and shows Connected is not the proof; the line through the tunnel and the silent witness are.
4. **The listing is checked like the app's strings, and the assets made from the app's own** (`docs/m11/store-listing.md`, `scripts/check_listing_claims.py`, `scripts/release/store_assets.py`). The title, short and full descriptions, release notes and screenshot captions are fenced blocks and a table in one document; CI fails on any claim `CopyClaimsTest` forbids the app (coverage of all traffic or every app, a full or system-wide VPN, anonymity, hiding identity, blanket security, encrypting everything, protection, "no logs", games and calls, a guarantee) unless the sentence denies it, on Play's lengths and title words, on a placeholder in a block, and when the full description fails to say TCP, UDP blocked, ping, what the provider sees, not anonymous, Android's VPN feature and no VPN server. The icon is the adaptive icon's own geometry on brand teal at 512 px; the feature graphic the mark, the name and the short description; the screenshots the committed Roborazzi ones reframed to 9:16 under captions the same checker reads, in the listing's order; CI checks every committed asset's size, format and depth against Play's specifications, and that the folder is what the listing lists.
5. **The privacy policy page is generated from the app's strings and published with GitHub Pages** (`scripts/release/privacy_page.py`, `.github/workflows/pages.yml`; decision D9's default). The app's text, `docs/m9/privacy-policy.md` and the page come from one source; tests fail when any two differ; the page has no script and fetches nothing; the deploy job waits for the owner to turn Pages on (`PAGES_ENABLED`), so the workflow is green before then.
6. **Every declaration is written from what the app does, with the evidence beside it** (`docs/m11/declarations.md`): Data safety "no collection" (nothing to the developer; the traffic processed ephemerally; the user's own server the user's chosen destination), the content rating, target audience, the advertising ID, the foreground service of type `systemExempted` under Android's VPN-app exemption, the VpnService declaration with VPN as core functionality and the smoke's recording as its video, prominent disclosure before access (the onboarding's page and Android's consent). The encryption requirement is decision D2's, still the owner's: the recommendation stands — ask Play policy support before the first upload; the build flag option (b) is not implemented and is a follow-up if chosen.
7. **The release's identity and version**: name ProxyFlow (searched: no Android app of the name; a Chrome extension "ProxFlow" one letter away; registers the owner's), package `app.proxyflow.android`, version 1.0.0 (11), versionCode up by one per upload. Decision D10 holds the owner's answers.
8. **Submission waits on the checklist** (`docs/m11/release-checklist.md`): the owner's answers, Play's requirements re-read on the day, the build's proof on the release commit, internal then closed testing with the twelve testers for fourteen days where the account requires it and the crash-free bar read from Android vitals, the listing and declarations entered, the keys backed up, and a sign-off with no open item.

## Alternatives considered

- **Signing in CI with a key the workflow generates and keeps as an artifact**: a key in an artifact is a key in a download; the owner's key stays with the owner, and the run key is thrown away.
- **Skipping the signed smoke, since M10's device suite already proves routing**: M10 ran the debug build with test hooks; Play ships the release bundle's splits, signed, minified, with no hooks — the one thing M10 never installed.
- **Hand-written store assets**: a designer's icon and framed screenshots could look better; what the app shows is what the pictures must show, and Play's rule against misleading screenshots is met by reframing the app's own.
- **A hosted privacy policy on a third-party page builder**: one more account and one more script-laden page; a generated static page from the app's own strings cannot drift from the app.
- **Deciding D2 here**: it is a product and policy choice, not an engineering one; ADR-0005 left it to the owner and the checklist keeps it open until answered.

## Consequences

- The project holds no secret; the owner holds the upload key and the three repository secrets, and a lost key is replaced through Play's upload-key reset without touching the key phones trust.
- The engine job runs twice per push (once for each workflow): the price of a release workflow the owner can start on its own.
- Every push proves the release path in run-key mode (about 25 minutes more CI per push: a build and two emulators); the hand-started run with the secrets gives the bundle to upload.
- The listing cannot drift from the app's limits without failing CI; the assets cannot drift from the listing.
- The privacy policy page needs the owner to turn Pages on once; until then the URL in the listing is a promise.
- Closed testing and the physical-phone checklist are the owner's time: fourteen days at least, with twelve people.
