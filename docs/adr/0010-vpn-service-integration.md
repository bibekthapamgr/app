# ADR-0010 — VPN service integration: connect sequence, session ownership, failure handling

**Status:** Accepted 2026-10-31 (technical decisions delegated by the owner, as for ADR-0001 to ADR-0005); implemented in M5, revised 2026-11-01 after the first emulator runs and two independent reviews (routing wait, one interface per connection, pre-flight pass rule, credentials bound to the attempt's profile, profile deletion). The pre-flight target is an engineering default inside open decision D6 · **Date:** 2026-11-01

## Context

M5 connects the M4 engine to Android's VPN interface. M1 already fixed the outline: consent with `VpnService.prepare()` behind an explainer (J4, B9), a pre-flight proxy handshake before the VPN exists (J5), the `Builder` settings (`docs/m1/06-architecture.md` §4), a foreground service of type `systemExempted` (ADR-0007), "Connected" only after a successful handshake, and the error catalogue (`docs/m1/04-ux-screens-and-error-states.md` §4). What M1 left open, and this record decides: where the session lives and who owns the TUN descriptor, what the pre-flight check contacts and which answers pass it, when "Connected" is true, what happens when the engine dies, Android revokes the VPN or the connection's profile is edited or deleted, how duplicate starts and profile switches are handled, and how all of it is proven on emulators. Reconnecting after network changes, offline handling and the escalation rule are M7; the kill switch and Always-on lockdown are M8; the Quick Settings tile, onboarding and the rest of J11 (picking another profile or editing the active one while connected) are M9.

## Decision

1. **Module `:core:vpn`** holds `ProxyFlowVpnService`, `VpnSession`, `VpnRuntime`, the app's `ConnectionController` and the notifications. Screens keep talking only to `ConnectionController` (ADR-0008); its `state` is a `StateFlow<ConnectionState>` (status, profile id and name, the connection's own copy of the profile's settings, connect step, connected-since time, last error).
2. **One session per process, one thread of control.** `VpnRuntime` (built once by the app's `AppContainer`) owns the only `VpnSession`. Every transition — connect, pre-flight result, establish, engine start, Android routing apps into the interface, engine failure, revocation, disconnect, the service attaching or going away — is an event handled one at a time on a serial dispatcher (`Dispatchers.IO.limitedParallelism(1)`), so no two can interleave; engine calls block there, never on the main thread. Only the pre-flight check and the wait for Android's routing run beside it, so a disconnect or a revocation is never stuck behind them; their late answers are ignored, and an exception nothing in them expected becomes a failure of the connection (handled like any other), never a crash that would drop a held VPN. The service is a host the session uses for what needs a `VpnService` instance (consent check, `establish()`, `protect()`, Android's view of the VPN network, the foreground notification): the session starts it when a connection needs it and waits up to 10 s for it to attach; the service stops itself with `stopSelfResult()`, so a start that arrived meanwhile is never lost. The session owns the TUN `ParcelFileDescriptor`; the engine reads it but never closes it (M4), and the session closes it only after the engine has stopped.
3. **Connect sequence.** Consent still valid (`prepare()` is null) → `startForeground` (type `systemExempted` on Android 14+) → **pre-flight** on its own coroutine: the profile's credentials, then one tunnel through the proxy with the same adapters (`ProxyEngine.probe`) on a protected socket → the credentials read again for the engine → `Builder.establish()` with the M1 settings (`198.18.0.1/32` and `fd00:66::1/128` from the engine's `NetworkPlan`, routes `0.0.0.0/0` and `::/0`, DNS `198.18.0.2`, MTU 9000 — the engine runs with the same MTU — the app itself excluded, the default network as underlying network until M7 names it, metered as it is, non-blocking, never `allowBypass`) → engine start on the descriptor → **Android routes apps into the interface** → **Connected**. `establish()` returns before Android has created the VPN network and its per-app routing rules; on the first emulator runs, traffic sent right after it still took the normal network (a DNS query to the emulator's resolver, connections straight to the destination). So the session polls `ConnectivityManager` (every 50 ms, up to 10 s; `ACCESS_NETWORK_STATE`) until a VPN network that leads into the new interface (its name read from the descriptor, `/proc/self/fdinfo`) is reported VALIDATED — which Android reports for a VPN only after the network was created with its routes, DNS servers and app rules — and that was not already there on that interface before (a network still being torn down). Callbacks can't be used: they are never told about a VPN that excludes the caller, as ProxyFlow's does. The interface is created only by a first connect; it serves the whole connection (§5). Until Connected, any failure — the check, `establish()`, the engine, Android never routing — takes the new interface down again and ends in Disconnected with the code (board B6b): the user was never connected. Credentials are always read together with a check of the stored profile against the copy the attempt started with: if its protocol, server, port, TLS settings or sign-in changed meanwhile, nothing is decrypted and the attempt starts over with the new settings, so a password is never sent to a server it was not saved for.
4. **Pre-flight target: `connectivitycheck.gstatic.com:443`, CONNECT only; it passes only when the proxy opens the tunnel.** HTTP proxies check sign-in only on a `CONNECT`, so the check needs a destination; it opens the tunnel and closes it at once, sending no bytes through it. The host is the one Android's own connectivity check uses, and port 443 is the one proxies allow by default (Squid's `SSL_ports`). Every other answer fails the check with its code, and Home explains each (B6b): a refusal by the proxy (`TARGET_NOT_ALLOWED`: HTTP 403, SOCKS5 0x02), which providers also send for an expired plan or an address that isn't allowed; a general failure (`PROXY_GENERAL_FAILURE`: SOCKS5 0x01, or another HTTP status such as 401, 402, 404, 429 or 500); a destination the proxy could not reach (`TARGET_UNREACHABLE`, `TARGET_REFUSED`: HTTP 502–504, SOCKS5 0x03–0x06), which for this host means the proxy has no working way out to the Internet; and a request the proxy doesn't support (`TARGET_UNSUPPORTED`). Each of these would otherwise show Connected while apps' connections fail. The price: a proxy that blocks or can't reach this one host can't connect, even if other sites would work; the target is one constant (`VpnSession.PREFLIGHT_TARGET`), part of open decision D6 (what "Test connection" contacts), and the privacy policy must name it. A cancelled check (Disconnect, another profile) ends at once: the sockets it protects are duplicated as it opens them, and a cancel shuts the duplicates down from the cancelling thread, so the engine's blocking call returns instead of running into its 15 s timeout; the engine's own descriptors are never closed behind its back.
5. **Duplicate starts and switching: one interface per connection.** `connect()` for the profile that is already connecting, reconnecting or connected does nothing; `connect()` for a profile that no longer exists leaves a running connection alone. Once the user has been connected, `connect()` for another profile — or Restart of a blocked one — **reconnects**: the engine stops at once (existing flows end, J11), the interface stays, so apps' traffic is held, the new profile is checked, and the next engine starts **on the same interface**; Connected follows once Android still routes apps into it (§3, at once in practice). No second interface is created: on `establish()` Android brings the previous interface down at once (`jniReset`) and moves the VPN network's routes to the new one only afterwards, asynchronously, and in between its fall-through rule sends traffic of the VPN's network to the normal network — apps' connections and DNS queries would leave outside the tunnel. The interface's settings never change between profiles (they come from the engine's network plan), so nothing is lost. If anything fails on the way, the connection is **Blocked** with its code and keeps the interface, so leaving the protected state always takes an explicit "Stop and use normal network" (`docs/m1/03-user-journeys.md`); without the user's consent any more (another VPN app took over), Android has already removed the VPN and the connection ends with `VPN_PERMISSION_DENIED` instead of claiming to hold traffic. `disconnect()` while connecting cancels the check and the attempt ends without ever reporting Connected.
6. **Engine failure fails closed.** When the engine reports `engine_failed` (its packet loop ended without `Stop`) on a connected session, the session stops it (releasing its goroutines and credentials) and keeps the VPN interface with nothing reading it, so apps' traffic is held, and shows `ENGINE_STOPPED` (status Blocked) with Restart and "Stop and use normal network". Restart runs the connect sequence again as in §5. During a first attempt (before Connected) it ends the attempt like any other failure (§3).
7. **Revocation.** `onRevoke()` (another VPN app started, or the user removed the permission) stops the engine, closes the descriptor, ends the foreground service and reports `VPN_REVOKED` (board B6d) in the app and in a notification on the "Connection problems" channel. Android has already removed the VPN, so apps use the normal network unless the system lockdown is on (M8).
8. **Service lifecycle and profiles.** The session starts the service with `ACTION_CONNECT`; the notification's actions send `ACTION_DISCONNECT` and `ACTION_RESTART`; a start by Android with `VpnService.SERVICE_INTERFACE` (Always-on) connects the profile the user explicitly chose, or stops when there is none. `START_NOT_STICKY`: after process death the VPN is gone and the app restarts Disconnected, which is true. A destroyed service ends whatever connection is left. Deleting the profile a connection uses goes through "Disconnect and delete" in the profile list (J11), which says the connection ends and disconnects before deleting. Should the profile disappear any other way — also while an edit of it is being checked — its credentials are never used again: the engine stops, an attempt that never connected ends, and once the user has been connected the connection stays Blocked (`PROFILE_DELETED`) until they stop it. Edits to the connected profile apply at the next connect; until then Home describes the connection with its own copy of the settings it runs (M9 decides how editing the active profile is offered while connected).
9. **Notifications.** Channel "Connection status" (low importance, silent) carries the foreground notification — Connecting (with the step and Cancel), Reconnecting, Connected (with a timer and Disconnect) or Blocked (with Restart and Disconnect); channel "Connection problems" (high importance) carries revocation. Tapping opens the app. The status notification is private with a public version without the profile name (threat model I-11). A connection's first status goes up at once (it is what puts the service in the foreground); later ones are at least 300 ms apart and the last state always gets through, because Android drops a package's notification updates beyond about five a second, which could leave a stale state showing. A stop that arrives late never removes a newer connection's notification.
10. **Permissions in the UI.** Connect shows the B9 explainer before the system consent dialog whenever `VpnService.prepare()` returns an intent; a refusal or back-press shows H1 (`VPN_PERMISSION_DENIED`), and nothing is started. On Android 13+ the notification permission is asked at the first Connect of each app run (Android itself stops asking after two refusals) until onboarding (A3, M9) takes it over; the VPN works without it.
11. **Diagnosis.** The session and the service record their lifecycle (connection steps by profile id, service starts and stops, Android's callbacks; never a credential, a server name or anything apps send) in logcat under the tag `ProxyFlowVpn` and in memory, so device-test failures report what happened. M7's local log builds on it.

## Alternatives considered

| Option | Assessment |
|---|---|
| **Session owned by a process-wide runtime, service as its host (chosen)** | One state machine however often Android creates or destroys the service; a connection that needs the service starts it |
| Session owned by each service instance | Simpler wiring, but a service destroyed and recreated mid-connection would run two state machines against one process-wide engine |
| Locks around a shared state | The same safety with more ways to get it wrong |
| A separate process for the service | Isolation, but state would have to cross processes; the engine already isolates per-flow failures |
| Handshake-only pre-flight | Impossible for HTTP proxies, which evaluate sign-in only on `CONNECT` |
| Pre-flight to a URL with an HTTPS request | Proves more, but sends a request through the user's proxy on every connect; kept for "Test connection" (D6) |
| Pass the check on any answer about the destination (the first M5 version) | A proxy that answers "plan expired" or "address not allowed" with 403, 402 or a SOCKS5 refusal would show Connected while nothing works: an invalid proxy must never show Connected |
| Pass the check when the proxy tried the destination but could not reach it (the second M5 version) | For Android's own connectivity host that nearly always means the proxy has no working way out: Connected while nothing works |
| A second check target before accepting a refusal | Two connections per connect, and a second host for the privacy policy, for the rare proxy that allows everything but the check's target (D6 can revisit the target) |
| Connected as soon as the engine runs on the new interface (the first M5 version) | Android applies the VPN's routing after `establish()` returns; the first emulator runs saw apps' DNS and connections take the normal network right after "Connected" |
| Wait for the VPN network with a network callback | The callback never reports a VPN that excludes the caller (API 31+), and ProxyFlow's excludes ProxyFlow |
| A new interface for each switch or restart, the old one closed once Android routed the new one (the second M5 version) | Android brings the old interface down inside `establish()` and moves the routes afterwards; its fall-through rule sends apps' traffic to the normal network in that gap |
| Close the interface when the engine dies, or when a switch fails | Simpler, but apps would silently fall back to the normal network: fail-open |
| End the connection when its profile is deleted from anywhere | Releases held traffic without the user's Stop; the list's "Disconnect and delete" is that explicit choice |
| Keep the old engine running while the new profile is checked | Traffic keeps flowing during a switch, but through the proxy the user just left; J11 asks for the switch to close existing flows |
| `specialUse` service type first | Needs a Play justification; `systemExempted` is meant for VPN apps (ADR-0007) and is verified on Android 14–16 in CI |

## Consequences

- The app gains `INTERNET`, `ACCESS_NETWORK_STATE`, `FOREGROUND_SERVICE`, `FOREGROUND_SERVICE_SYSTEM_EXEMPTED` and `POST_NOTIFICATIONS` (ManifestTest and `scripts/check_release_manifest.py` allow exactly these). Its APK carries the engine library (`libgojni.so` per ABI).
- Every connect sends one CONNECT for `connectivitycheck.gstatic.com:443` through the user's proxy; the privacy policy must say so (D6). A proxy that can't or won't open it fails to connect with the proxy's own answer, unless the failure was reaching the destination.
- Connecting takes a little longer: Android's routing (tens of milliseconds on emulators) is part of a first connect, and a connection whose interface Android never routes fails with `INTERNAL` after 10 s rather than claiming protection it doesn't give.
- An interface that itself stops working can't be restarted: Restart runs the next engine on it and fails the same way, and the user stops and connects again, which creates a new interface (nothing was routed before that connect, so there is no gap to leak through).
- After an engine failure, a failed switch or a deleted profile, apps are offline until the user restarts or stops; that is the intended fail-closed behaviour, and the notification says so.
- The app's own sockets bypass the VPN (excluded application, and the engine's sockets are protected), so tests that need traffic through the tunnel must make it from another identity: the instrumented tests use the shell.
- Proxy failures after connecting (the proxy dies, the password is changed) still show Connected until M7's escalation rule; until then each failed connection is refused, never sent around the proxy.

## Verification (M5)

JVM tests drive the session with a fake engine and a fake service through every transition above, including Android routing late, never, or to a stale network; switches and restarts on the one interface; an edit during the check, and a deletion during the re-check it causes; a check cancelled before it ran (no credentials decrypted) and while it ran (cut short, also with a single thread); exceptions in the check and in reading Android's networks; engine start failures of every kind; consent gone during a switch; and deletion while connected and while connecting. On emulators (API 29, 34, 35 and 36) the app's instrumented tests use the real service and engine: Android's own consent dialog (refused and allowed) behind the explainer, and `appops` for the other tests; TCP from the shell through the VPN to a destination behind real proxy servers on the CI runner (Dante for SOCKS5, Squid for HTTP CONNECT, both with sign-in, both able to reach the pre-flight target) that is reachable only by name; Android's VPN network ready and leading into the session's interface whenever the app says Connected; wrong passwords, a closed port and a silent proxy that never connect and never establish an interface; a switch to a silent proxy and on to a working one on the same interface, with traffic sent while it is under way and after it failed; revocation; an engine failure that holds traffic until Restart; repeated starts and connect/disconnect cycles that leave no interface, service, job or socket behind. Afterwards `scripts/m5_evidence.py` checks the destination's and the proxies' logs, logcat and packet captures of the emulator's uplink: every line arrived exactly once and through a proxy, no held line arrived, and nothing reached the destination or asked for its name directly.
