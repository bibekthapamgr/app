# ADR-0010 — VPN service integration: connect sequence, session ownership, failure handling

**Status:** Accepted 2026-10-31 (technical decisions delegated by the owner, as for ADR-0001 to ADR-0005); implemented in M5. The pre-flight target is an engineering default inside open decision D6 · **Date:** 2026-10-31

## Context

M5 connects the M4 engine to Android's VPN interface. M1 already fixed the outline: consent with `VpnService.prepare()` behind an explainer (J4, B9), a pre-flight proxy handshake before the VPN exists (J5), the `Builder` settings (`docs/m1/06-architecture.md` §4), a foreground service of type `systemExempted` (ADR-0007), "Connected" only after a successful handshake, and the error catalogue (`docs/m1/04-ux-screens-and-error-states.md` §4). What M1 left open, and this record decides: where the session lives and who owns the TUN descriptor, what the pre-flight check contacts, what happens when the engine dies or Android revokes the VPN, how duplicate starts and profile switches are handled, and how all of it is proven on emulators. Reconnecting after network changes, offline handling and the escalation rule are M7; the kill switch and Always-on lockdown are M8; the Quick Settings tile, onboarding and the rest of J11 (picking another profile or editing the active one while connected) are M9.

## Decision

1. **Module `:core:vpn`** holds `ProxyFlowVpnService`, `VpnSession`, `VpnRuntime`, the app's `ConnectionController` and the notifications. Screens keep talking only to `ConnectionController` (ADR-0008); its `state` is a `StateFlow<ConnectionState>` (status, profile, connect step, connected-since time, last error).
2. **One session per process, one thread of control.** `VpnRuntime` (built once by the app's `AppContainer`) owns the only `VpnSession`. Every transition — connect, pre-flight result, establish, engine start, engine failure, revocation, disconnect, the service attaching or going away — is an event handled one at a time on a serial dispatcher (`Dispatchers.IO.limitedParallelism(1)`), so no two can interleave; engine calls block there, never on the main thread. Only the pre-flight check runs beside it, so a disconnect or a revocation is not stuck behind a slow proxy; its late answer is ignored. The service is a host the session uses for what needs a `VpnService` instance (consent check, `establish()`, `protect()`, the foreground notification): the session starts it when a connection needs it and waits up to 10 s for it to attach; the service stops itself with `stopSelfResult()`, so a start that arrived meanwhile is never lost. The session owns the TUN `ParcelFileDescriptor`; the engine reads it but never closes it (M4), and the session closes it only after the engine has stopped.
3. **Connect sequence.** Consent still valid (`prepare()` is null) → `startForeground` (type `systemExempted` on Android 14+) → the profile and its credentials (`CREDENTIAL_UNREADABLE` stops here) → **pre-flight**: one tunnel through the proxy with the same adapters (`ProxyEngine.probe`), on a protected socket → the credentials read again for the engine → `Builder.establish()` with the M1 settings (`198.18.0.1/32` and `fd00:66::1/128` from the engine's `NetworkPlan`, routes `0.0.0.0/0` and `::/0`, DNS `198.18.0.2`, MTU 9000 — the engine runs with the same MTU — the app itself excluded, the default network as underlying network until M7 names it, metered as it is, non-blocking, never `allowBypass`) → engine start on the descriptor → **Connected**. Any failure before `establish()` leaves the phone's network untouched and ends in Disconnected with the code (board B6b). If the engine cannot start on a first interface, that interface is closed again and the attempt ends the same way: the user was never connected. Nothing is reported Connected before the engine runs on the new interface.
4. **Pre-flight target: `connectivitycheck.gstatic.com:443`, CONNECT only.** HTTP proxies check sign-in only on a `CONNECT`, so the check needs a destination; it opens the tunnel and closes it at once, sending no bytes through it. The host is the one Android's own connectivity check uses, and port 443 is the one proxies allow by default (Squid's `SSL_ports`). A target-level answer (`TARGET_*`, `PROXY_GENERAL_FAILURE`) proves the proxy is reachable and speaks its protocol — and, for SOCKS5 and HTTP answers other than 403, that it accepted the sign-in, which comes first — so the connection proceeds; any other code fails the check. The target is one constant (`VpnSession.PREFLIGHT_TARGET`); it is part of open decision D6 (what "Test connection" contacts) and the privacy policy must name it.
5. **Duplicate starts and switching.** `connect()` for the profile that is already connecting, reconnecting or connected does nothing. While an interface is up, `connect()` for another profile — or Restart of a blocked one — **reconnects**: the engine stops at once (existing flows end, J11), the interface stays, so apps' traffic is held, the new profile is checked, and its interface is established before the old one is closed (Android swaps them), so nothing leaves outside the tunnel at any point. If that check fails, the connection is **Blocked** with its code: once connected, leaving the protected state always takes an explicit "Stop and use normal network" (`docs/m1/03-user-journeys.md`). `disconnect()` while connecting cancels the check and the attempt ends without ever reporting Connected.
6. **Engine failure fails closed.** When the engine reports `engine_failed` (its packet loop ended without `Stop`), the session stops it (releasing its goroutines and credentials) and keeps the VPN interface with nothing reading it, so apps' traffic is held, and shows `ENGINE_STOPPED` (status Blocked) with Restart and "Stop and use normal network". Restart runs the connect sequence again as in §5.
7. **Revocation.** `onRevoke()` (another VPN app started, or the user removed the permission) stops the engine, closes the descriptor, ends the foreground service and reports `VPN_REVOKED` (board B6d) in the app and in a notification on the "Connection problems" channel. Android has already removed the VPN, so apps use the normal network unless the system lockdown is on (M8).
8. **Service lifecycle.** The session starts the service with `ACTION_CONNECT`; the notification's actions send `ACTION_DISCONNECT` and `ACTION_RESTART`; a start by Android with `VpnService.SERVICE_INTERFACE` (Always-on) connects the profile the user explicitly chose, or stops when there is none. `START_NOT_STICKY`: after process death the VPN is gone and the app restarts Disconnected, which is true. A destroyed service ends whatever connection is left. Deleting the profile a connection uses ends that connection (J11's "Disconnect and delete"), so deleted credentials are never used again.
9. **Notifications.** Channel "Connection status" (low importance, silent) carries the foreground notification — Connecting (with the step and Cancel), Reconnecting, Connected (with a timer and Disconnect) or Blocked (with Restart and Disconnect); channel "Connection problems" (high importance) carries revocation. Tapping opens the app. The status notification is private with a public version without the profile name (threat model I-11).
10. **Permissions in the UI.** Connect shows the B9 explainer before the system consent dialog whenever `VpnService.prepare()` returns an intent; a refusal or back-press shows H1 (`VPN_PERMISSION_DENIED`), and nothing is started. On Android 13+ the notification permission is asked at the first Connect of each app run (Android itself stops asking after two refusals) until onboarding (A3, M9) takes it over; the VPN works without it.

## Alternatives considered

| Option | Assessment |
|---|---|
| **Session owned by a process-wide runtime, service as its host (chosen)** | One state machine however often Android creates or destroys the service; a connection that needs the service starts it |
| Session owned by each service instance | Simpler wiring, but a service destroyed and recreated mid-connection would run two state machines against one process-wide engine |
| Locks around a shared state | The same safety with more ways to get it wrong |
| A separate process for the service | Isolation, but state would have to cross processes; the engine already isolates per-flow failures |
| Handshake-only pre-flight | Impossible for HTTP proxies, which evaluate sign-in only on `CONNECT` |
| Pre-flight to a URL with an HTTPS request | Proves more, but sends a request through the user's proxy on every connect; kept for "Test connection" (D6) |
| Close the interface when the engine dies, or when a switch fails | Simpler, but apps would silently fall back to the normal network: fail-open |
| Keep the old engine running while the new profile is checked | Traffic keeps flowing during a switch, but through the proxy the user just left; J11 asks for the switch to close existing flows |
| `specialUse` service type first | Needs a Play justification; `systemExempted` is meant for VPN apps (ADR-0007) and is verified on Android 14–16 in CI |

## Consequences

- The app gains `INTERNET`, `FOREGROUND_SERVICE`, `FOREGROUND_SERVICE_SYSTEM_EXEMPTED` and `POST_NOTIFICATIONS` (ManifestTest and `scripts/check_release_manifest.py` allow exactly these); `ACCESS_NETWORK_STATE` arrives with M7's network monitor. Its APK carries the engine library (`libgojni.so` per ABI).
- Every connect sends one CONNECT for `connectivitycheck.gstatic.com:443` through the user's proxy; the privacy policy must say so (D6).
- After an engine failure, or a failed switch, apps are offline until the user restarts or disconnects; that is the intended fail-closed behaviour, and the notification says so.
- The app's own sockets bypass the VPN (excluded application, and the engine's sockets are protected), so tests that need traffic through the tunnel must make it from another identity: the instrumented tests use the shell.
- Proxy failures after connecting (the proxy dies, the password is changed) still show Connected until M7's escalation rule; until then each failed connection is refused, never sent around the proxy.

## Verification (M5)

JVM tests drive the session with a fake engine and a fake service through every transition above. On emulators (API 29, 34, 35 and 36) the app's instrumented tests use the real service and engine: Android's own consent dialog (refused and allowed) behind the explainer, and `appops` for the other tests; TCP from the shell through the VPN to a destination behind real proxy servers on the CI runner (Dante for SOCKS5, Squid for HTTP CONNECT, both with sign-in) that is reachable only by name; wrong passwords, a closed port and a silent proxy that never connect; a profile switch; revocation; an engine failure that holds traffic until Restart; repeated starts and connect/disconnect cycles that leave no interface, service, job or socket behind. Afterwards `scripts/m5_evidence.py` checks the destination's and the proxies' logs, logcat and packet captures of the emulator's uplink: every line arrived exactly once and through a proxy, no held line arrived, and nothing reached the destination or asked for its name directly.
