# ADR-0013 — Kill switch, process death and security hardening (M8)

**Status:** Accepted 2026-11-04 (technical decisions delegated by the owner, "Timi nai decide gara"; implemented in M8) · **Date:** 2026-11-04

## Context

M8 asks ProxyFlow to fail safely when the proxy or the engine fails, and to harden the app: app-level fail-closed behaviour that never routes supported traffic directly when the engine fails; an honest account of Android's own lockdown (Always-on VPN with "Block connections without VPN"), which an app toggle cannot guarantee, with guidance to Android's settings; tests of tunnel failure, proxy disconnect, network changes, permission revocation and process death; a review of credential encryption, key invalidation, log redaction and exported components; least-privilege manifest settings and secure defaults; bounds on concurrent flows, buffers, retries and log storage; a dependency vulnerability scan and code review; and the known limitations and threat model brought up to date. Its acceptance criteria: an engine failure never silently sends supported traffic directly; system lockdown is never presented as guaranteed by an app toggle; no critical or high security issue is open before release; sensitive data is absent from logs, crash reports and exported diagnostics; resource limits are tested under load and malformed input; permission revocation and disconnect clean up resources.

What M4–M7 left: while ProxyFlow's VPN interface exists, nothing goes around the proxy — a failed engine, a proxy that stops answering, a reconnection, an offline phone all hold traffic at the interface (ADR-0004, ADR-0010 §5, ADR-0012 §6). What none of that covers is the interface itself going away: the user disconnecting, another VPN app taking over (revocation), and ProxyFlow's process ending — Android removes the VPN with it, and apps then use the normal network. Only Android's Always-on VPN with "Block connections without VPN" keeps them off it then, and only the user can turn that on. M5 started ProxyFlow for Always-on VPN with the chosen profile (ADR-0010 §8) but checked the proxy before creating the interface, like a user's connect. M7 left one proxy failure unescalated: a SOCKS5 proxy that answers its sign-in but never a connection request (docs/m6/routing-and-limitations.md §4).

## Decision

1. **Two kill switches, neither a toggle.** ProxyFlow's own ("in-app kill switch") is what the engine and the session already do while connected: traffic is held, never sent around the proxy (ADR-0004, ADR-0010, ADR-0012). It is always on and has no setting. Android's ("system kill switch") is Always-on VPN set to ProxyFlow with "Block connections without VPN": Android then keeps apps off the network whenever ProxyFlow's VPN is not running — after a crash, after Android ends the process, while another VPN app holds the VPN. No app can turn it on; only the user can, in Android's VPN settings. Settings (E1, E1b) shows both, the second with what Android last said and when; Home shows on B2 what happens if ProxyFlow stops, and on B6d (the VPN revoked) a card to set Android's up until it is on; E2 is the guide: what it does and doesn't do, the four steps, that menu names vary by maker, that ProxyFlow can't turn it on, that Android may not start ProxyFlow again after ending its process, that some of Android's own services bypass any VPN, and a button to Android's VPN settings (`Settings.ACTION_VPN_SETTINGS`, then the network settings, then Settings; each Android's own screen, nothing passed to it). The copy never says or implies that ProxyFlow guarantees blocking (`CopyClaimsTest` keeps the rest of its rules).
2. **What Android says, as Android said it.** Android answers whether Always-on VPN is set to ProxyFlow and whether it blocks without VPN (`VpnService.isAlwaysOn()`, `isLockdownEnabled()`, API 29+) only while ProxyFlow's VPN interface exists. The session reads it once an Always-on VPN start has its interface up (before the proxy is checked), after each connection and reconnection, when Android starts the service for Always-on VPN while connected (the user just turned it on), and when Home, Settings or the guide is shown while an interface exists; it keeps the reading with its wall-clock time in a DataStore file of its own (`protection`), logs it (`system_kill_switch`, always-on yes/no, blocks yes/no) and the lifecycle log line `system kill switch: on|always_on_only|off` when it changed. The screens show "as Android says now" while connected and "as Android said at <time>" otherwise, "not checked yet" before the first reading — never a status the app could not have known.
3. **Always-on VPN holds traffic first.** When Android starts the service for Always-on VPN (the `android.net.VpnService` action, no profile in the intent), the session connects only the profile the user chose explicitly ("Use this proxy", or Connect on Home, which now records the profile it connects as the choice) — never a fallback (ADR-0010 §8). It establishes the VPN interface before the proxy check, so from Android's start on, apps' traffic is held at the interface instead of using the normal network while the check runs; Home says so while it connects (B3b: apps' traffic held until ProxyFlow reaches the proxy), and stopping there asks first, as on B5 and B6, since it sends apps to the normal network; the status notification offers Disconnect then, as while reconnecting, not the Cancel of a user's connect, which leaves the phone as it was. A check that fails in a way that may pass (`RetryPolicy.recoverable`: unreachable, timeout, DNS, TLS handshake, protocol, general failure, internal) goes on as a connection that broke: reconnecting on its own (`always_on_start`, B5 "Starting as Always-on VPN"), traffic held, bounded as in ADR-0012 §6; a refused sign-in or certificate blocks at once (B6a, B6c). With no profile chosen nothing connects and the user is told (`ALWAYS_ON_NO_PROFILE`, a problem notification and B6b "Choose a proxy for Always-on VPN"): ProxyFlow never picks a proxy for the user, so with blocking on, apps have no network until they choose one.
4. **A process that ends while connected is found.** When a profile's session first holds traffic (an Always-on VPN start, or a switch to it with the interface kept) it writes a marker, and when the session first connects it writes it again with the session's start — not on a reconnection or a restart of the same profile; a switch to another profile writes that profile's in its place as the switch begins, connected or not, and a switch back writes the first one's afresh. The marker: the profile's random id, the session's start (until it has connected, when traffic began to be held for it), the process id and the phone's boot count (`Settings.Global.BOOT_COUNT`). Every end of the session — disconnect, failure before connecting, revocation, the service destroyed — removes it, in the same ordered queue as the other writes. A process that ends with the connection up leaves it. The next process reads it before anything else it writes, off the session's loop (Android's answer can be slow, and the session never waits for it), and asks Android how that process ended: a different boot count is a restart of the phone; on Android 11+ the process's `ApplicationExitInfo` (its record for that pid, if newer than the session's start; its description is never read, as it can hold an exception's message) gives the reason — low memory, a crash, a native crash, not responding, killed by a signal, force-stopped, updated, a permission changed, other — and the time; Android 10 says nothing (`unknown`). The interruption, with Android's kill switch as ProxyFlow last read it before that process ended, replaces the marker in one write: until that write the marker stays, so a process that ends before it recorded the interruption leaves it to the next one, and an interruption is never there without its marker gone. It is logged as an error (`session_interrupted`, the reason, whether the end time is exact, the session's length up to it, whether blocking was on), dated when the process ended where Android says, and kept for Home until the user dismisses it or connects again while Home shows it — one found after Home last looked is not cleared unseen. The store's flows read DataStore again after each of its own writes, and a write once begun is finished even if its caller is cancelled: DataStore before 1.3.0 could leave out a write for a collector that began while that write was on its way, which on the emulators (1.1.7) kept an interruption from a waiting test, and could have kept it from Home. ProxyFlow now uses DataStore 1.3.0, which fixed that for every store (1.3.0-alpha03), and the protection store reads again all the same. Home's notice says when and why, and what it meant — by the kill switch kept with it, not by what Android says later: apps used the normal network from then on, unless Android's kill switch was on then, in which case apps had no internet until it connected again — with "Set up system kill switch" while it is not on now. The next start connects nothing of its own accord (§5).
5. **No reconnect of its own on the next start.** The next process may start for any reason (the user opening the app, a test, Android); connecting without the user would be a surprise, and Android's Always-on VPN is the supported way for a VPN to run without the user — Android starts it at boot and when it is set. Android did not start ProxyFlow again after its process was killed on the CI emulators while the failure injection probed (26 to 31 s after the kill on API 29, 34, 35 and 36, in every attempt of the verified run, Always-on VPN with blocking on; the script looks for ProxyFlow's "always-on start" then): with blocking on, apps then stay offline until the user opens ProxyFlow and connects — at least for that long, and it may be for good. The guide (E2) and the limitations say so.
6. **A SOCKS5 proxy that leaves connection requests unanswered makes the session reconnect.** The engine counts connection requests a SOCKS5 proxy left unanswered in a row (it answered the method selection and the sign-in, not the request, within the handshake's deadline) and the different sites among them (a hash of the target's host — its name or address, not its port — at most 8 kept); any working connection, any answer from the proxy, and 2 minutes without another unanswered request start the count over (so an idle phone whose apps reach two dead sites now and then never adds up to a reconnection), and ADR-0012 §6 still counts each such failure as the site's. Once 3 in a row went unanswered to at least 2 different sites, the session reconnects (`proxy_unanswered`, B5 "Your proxy isn't answering"). One slow site never does: it is one site, and anything that works meanwhile starts over.
7. **Crash reports get sanitized exceptions.** `CrashReports` puts a handler in front of the one Android installed (in the application's `onCreate`, before anything else can fail): an exception that reaches the top of a thread is passed on as a copy of the same class with every message — its causes' and suppressed exceptions' too — passed through `LogSanitizer`, and the same stack traces; a class that can't be made again with only a message, or that builds its own message, is reported under its name with the sanitized message; one whose message fails is reported with "[message withheld]"; out-of-memory is passed as it is. Whatever the exception does, Android's handler runs next with something — it is what ends the process and keeps the report — down to a stand-in made up front that names nothing. Android's crash report (dropbox, and Google Play's crash reports, which read the same) then holds no address, host name, `user:password@` or long token from a message. A Lint check, `ExceptionSecret` (beside `LogSecret`), fails CI on ProxyFlow's own code that builds an exception's message from a credential, a server or destination, bytes, a profile or another exception's message, so ProxyFlow's own messages stay codes and fixed words. What no app can change: Android's runtime writes an uncaught exception, message and all, to the phone's log (logcat) before any app handler runs; logcat is readable by the app itself and by a computer with USB debugging (adb), not by other apps.
8. **Taps through another app's window are dropped.** The actions that send apps to the normal network or delete data — Disconnect, "Stop and use normal network", Delete proxy, Discard changes, Clear log — drop a tap whose touch Android marks obscured (`FLAG_WINDOW_IS_OBSCURED`, the flag Android's own `filterTouchesWhenObscured` checks), with a short message at most every 3.5 s however many taps arrive; a gesture that becomes obscured before the finger lifts is dropped whole (threat model S4). `FLAG_WINDOW_IS_PARTIALLY_OBSCURED` is not checked: Android sets it whenever any window overlaps any part of ProxyFlow's, where the finger is or not, so a chat bubble in a corner would make these actions unusable. Android's own VPN consent dialog is Android's.
9. **Secure defaults written out.** The app declares a network security config: no cleartext for Android's HTTP stacks, the system's certificate authorities only — no user-installed or bundled CA, no per-domain exception, no pin override — which Android's trust manager, and so ProxyFlow's TLS to the proxy, follows (ADR-0011); `scripts/check_release_manifest.py` fails the build if the file allows more, in `res/xml` or any qualified variant of it (`xml-v31`…) or the release build type's own resources, and if what the release APK itself ships for it, or for either backup rule file, fails the same checks in any configuration it ships (`aapt2 dump resources`, then `aapt2 dump xmltree` of each file): a library's file of the same name and qualifiers loses to the app's, but a qualified variant the app lacks ships beside it and applies where it matches, and the release build type's own copy replaces main's. aapt2's printout is read strictly: anything these files never hold — a namespace, text, a name or value of another form, a value over several lines, a line out of place — reads as no file and fails, since aapt2 prints names, values and text unescaped and a crafted file could otherwise print lines that read as other elements. The rest stays as M2–M7 set it and the release check enforces: the permissions on the allow-list only, backups and device transfers off, not debuggable, the VPN service not exported and bound only by Android, nothing exported without a permission but the launcher activity, notifications' `PendingIntent`s immutable.
10. **Bounds, tested.** The engine's: at most 1,024 TCP flows including set-ups (`MaxConns`, the rest refused with `CONNECTION_LIMIT`), at most 512 handshakes held while tunnels are set up (`MaxInFlight`, SYNs over it dropped and counted, the apps retry), 256 DNS sockets and 32 DNS-over-TCP connections, 64 KiB netstack buffers per flow (at most twice that) and 32 KiB relay buffers, 15 s per tunnel set-up, 5 min idle, 1,024 queued events (dropped and counted past that), 16,384 placeholder names; new engine tests open 120 connections at once at a limit of 24 and flood 48 handshakes at a limit of 8 against a proxy that never answers, and write 4,000 malformed packets of every kind into the TUN, and a fuzz target (`FuzzPacketLoop`) writes any bytes as a packet, in CI for 30 s each run. The app's: 8 reconnect attempts over about two minutes, the diagnostic log's 5,000 entries and 24 hours, its writer's 1,000 pending entries, the VPN lifecycle log's 200 lines in memory.
11. **Known vulnerabilities fail the build.** Each CI run asks OSV (osv.dev) about every library the release build ships, at its resolved version (`scripts/osv_scan.py` over `:app:dependencies --configuration releaseRuntimeClasspath`): an advisory rated HIGH or CRITICAL — the higher of its own rating and its CVSS v3 score — or not rated at all fails, unless `scripts/osv_allowlist.json` names it with why it can't reach ProxyFlow and a date to look again. OSV not answering fails the step, and so does a line of Gradle's tree that can't be read or a library Gradle could not resolve (a module another replaced is asked at what replaced it). The Go engine's dependencies stay with govulncheck in the engine job.

## Alternatives considered

- **An app toggle labelled "Kill switch" that turns on blocking**: no app can turn on Android's lockdown (`DevicePolicyManager.setAlwaysOnVpnPackage` needs a device owner), and a toggle that only changed ProxyFlow's own behaviour would read as a guarantee it is not — the acceptance criterion forbids it. ProxyFlow's own fail-closed behaviour has no off switch to offer.
- **Reconnect automatically when the next process finds an interrupted connection**: the next process may be started by anything, and connecting without the user's knowledge — possibly on another network, hours later — is the kind of surprise a VPN should not spring. Android's Always-on VPN is the user's way to have ProxyFlow connect by itself, and it is Android's to restart.
- **Check the proxy first on an Always-on VPN start, as a user's connect does**: with "Block connections without VPN" off, apps would use the normal network for the length of the check (seconds, or the check's whole timeout when the proxy is away) right after Android started the VPN the user wants always on.
- **Read the kill switch's status from `Settings.Secure`** (`always_on_vpn_app`, `always_on_vpn_lockdown`): hidden settings, not readable by apps on current Android, and different per version. Android's public answer is the `VpnService` one, available only while the VPN runs — so the status is shown as "as Android said at".
- **`filterTouchesWhenObscured` on the whole window**: it drops every obscured tap, also on harmless screens, with no message — the user would see taps do nothing whenever any overlay (a chat head, a screen dimmer) is up. Only the actions that let traffic out or delete data are guarded, and say why.
- **No crash handler, relying on ProxyFlow never putting secrets in messages**: Lint covers ProxyFlow's own code, not a library's; the handler covers what reaches the top of a thread whatever its source.
- **`FLAG_SECURE` on the proxy form**: the password is masked unless the user shows it, and `FLAG_SECURE` would also block the user's own screenshots for support and some accessibility tools. Left out for V1.
- **A vulnerability scanner with its own database (OWASP Dependency-Check)**: slower, needs the NVD feed and an API key to be reliable; OSV aggregates GitHub's and the ecosystems' advisories for Maven and answers in seconds.

## Consequences

- Behaviour changes from M7, deliberately: an Always-on VPN start establishes the interface before the proxy is checked and retries a failing proxy with traffic held; Connect on Home makes the connected profile the chosen one, so Always-on VPN later connects what the user last connected; a SOCKS5 proxy that leaves connection requests to several sites unanswered no longer leaves the session Connected with every connection failing.
- After process death, with Android's kill switch off, apps use the normal network until ProxyFlow connects again — ProxyFlow can't prevent it and says so afterwards. With it on, apps have no network until the user opens ProxyFlow (Android did not restart it on the emulators).
- The kill switch's status can be out of date while ProxyFlow is not connected (the user may have changed it in Android's settings); the screens say when it was read.
- Android's own pre-handler still writes an uncaught exception's message to logcat; ProxyFlow's own messages hold no secrets (Lint), so what could appear there is a library's message — readable only by ProxyFlow and adb.
- A dependency advisory can now fail a build that changed nothing; the allow-list with its review date is the way through.
