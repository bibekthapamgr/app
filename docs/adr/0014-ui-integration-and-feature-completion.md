# ADR-0014 — UI integration and feature completion (M9)

**Status:** Accepted 2026-11-04 (technical decisions delegated by the owner, "Timi nai decide gara"; implemented in M9) · **Date:** 2026-11-04

## Context

M9 asks for a coherent, complete free app with no mock functionality: every screen connected to the real repositories, service state and engine state; onboarding that explains what a proxy must be and why Android asks about a VPN; the Home, Profiles, Add/Edit, Settings, Logs and About/Privacy screens finished, with empty and loading states, confirmations and recovery actions; theme selection and accessibility labels; privacy policy, help and open-source notices; no placeholder button, fake counter or simulated connection state; and the UI checked on small screens, large fonts and dark mode. "Connected" must keep coming from the engine and the proxy, never from the UI.

What M2–M8 left: "Test connection" answered "not available yet" through `UnavailableConnectionTester` (honest, but a placeholder); the profile list had no Test and showed no result; Home's Change went to the Profiles tab instead of the picker the boards draw (B8); Settings had no log settings and a "coming later" banner; About had no privacy policy, help or licences; there was no first-launch onboarding; the notification permission was asked when the user first tapped Connect; the Quick Settings tile (B11) did not exist.

## Decision

1. **"Test connection" is the pre-flight check on the engine.** `EngineConnectionTester` (core/vpn) runs the same check connecting makes first (ADR-0010 §4), on the same engine and so with the same TLS trust: the proxy's TCP and TLS, its sign-in, and one tunnel to the pre-flight target (`connectivitycheck.gstatic.com:443`, open decision D6) opened and closed again with nothing sent through it — without the VPN, so the phone's network never changes. ProxyFlow's own UID is outside its VPN (`addDisallowedApplication`), so a test while connected reaches the tested proxy directly. The time it reports is the engine's: from dialling the proxy to the tunnel being open. Credentials go only to the proxy tested: a typed password, or — with the form's password left empty — the saved one under the rule of saving (`sameCredentialTargetAs`: same protocol, server, port, username and TLS settings), never to another server, never with another username. A cancelled test (Cancel, an edit, leaving the screen) stops its connection to the proxy at once: `ShutdownGuard` shuts the test's sockets down, as for a cancelled pre-flight check; only a lookup of the proxy's name the engine is still making can't be cut short, and ends by itself. Only the engine's own answer can be a pass; a tester that throws, an engine that fails to load or a Keystore that is unavailable is `INTERNAL`, a failure. A failure found before any proxy is asked — no password to send, a saved password this phone can no longer read, a test that couldn't start — is marked as not the engine's (`ConnectionTestResult.Failed.fromEngine` false; every failure says which it is). The form asks for the password itself before a test the saved one can't go with, so "no password to send" reaches it only when the profile was changed or deleted since the form opened, and it says that nothing was sent and to type the password; an unreadable saved password asks for it again ("Re-enter your password"), as connecting does. `UnavailableConnectionTester` is gone, and `UnavailableConnectionController`, used only by tests, moved to core:testing.
2. **A test's result is kept with the profile while it still describes it.** Room v3 adds `last_test_at`, `last_test_code`, `last_test_latency` (`MIGRATION_2_3`, tested from v1 and v2). `recordTest` keeps a result only if the profile is still exactly as tested (the same save, `updatedAtMillis`, and the same server, compared as the rule of saving compares it: `ProfileValidator.hostKey`, the name trimmed, without an IPv6 literal's brackets or the root's trailing dot, in lower case); a later save keeps it only while the server and the credentials' key stay the same (a new name keeps it, a new password or port drops it); a copy starts untested. Three ways in: Test in the profile list (`testSaved`); the form's test of a saved profile as saved (its server, its saved password); and a form test of exactly the input that is then saved. A failure of the phone's own (`INTERNAL`) is shown, never kept; nor is one the tester found before asking a proxy, except a saved password this phone can no longer read, which describes the saved profile ("Re-enter your password"). The list (C2) and the picker (B8) show "Works · 182 ms · tested 2 min ago", the error catalogue's title for a failure ("Username or password rejected · tested 5 hours ago"), or "Not tested yet", with an icon as well as a colour. TalkBack announces a test's end: the line is a live region only while a test runs and while its result reads "just now", never for the minutes that pass after it, which would read a whole card out again each minute; the form's result is a live region too.
3. **One error catalogue for connecting and testing.** The proxy-check titles and messages moved from Home to core:designsystem (`proxyCheckErrorTitle/Message`); Home adds only its own (engine stopped, profile deleted, offline, Always-on without a profile). The form shows "Test failed: <title>", the catalogue's message and the code with the engine's sanitized detail, so a test and a connection say the same thing about the same failure; a pass says what it does not change: UDP stays blocked and ping unanswered.
4. **Picking a profile while a connection runs switches the connection (J11).** Home's Change and "Use another proxy" open the picker (B8): every profile with its last test, the one Home shows chosen (a radio group), Add proxy and Manage profiles. Picking one saves it as the choice and then asks the session to switch (`ConnectionController.switchIfConnected`), both even if the screen closes in between; a choice that can't be saved switches nothing. The session decides in order with everything else it was asked, so a Stop sent before the pick is never undone by it: it switches only a connection that exists then, on another profile. Once connected — or while an Always-on start holds traffic (`ConnectionState.holdsTrafficOnSwitch`) — that is the switch ADR-0010 §5 defines: flows end, traffic is held on the same interface until the new proxy is checked and blocked if it fails, never sent around a proxy. During a first connect apps still use the normal network, and a switch only checks the other proxy instead. Home offers the picker while disconnected, and B4 draws no Change; a connection can still start while the sheet is open (Always-on VPN, the Quick Settings tile), and the sheet then says what picking does before anything is picked, in the words for the state it is in. "Use this proxy" in the profile list does the same, and asks first whenever a connection runs on another saved profile ("Switch to …?"), in the same two wordings: once connected, what switching ends and that a failure keeps apps offline until ProxyFlow reconnects, the user tries again or stops; during a first connect, that the other proxy is checked instead. A connection whose profile was deleted (blocked already, and with no profile to name) switches at once. Before M9 the list changed the active profile under a running connection, so its ACTIVE and Home's connection could disagree. Editing the profile a connection runs on (board D9) asks before saving changes to how it reaches its proxy — its server, TLS or sign-in — and then reconnects with what was saved (`ConnectionController.reconnect`: the session runs the connect sequence again for the same profile, as a switch to itself, on the same interface); during a first connect it asks too, in words that say the new settings are checked instead and the phone's network stays as it is until then. Both questions follow the connection while they are open: their words change with its state, and they close, not applied, once no connection runs on the profile involved. A connection blocked because its profile was deleted isn't the form's: saving then makes a new profile and asks nothing. A new name alone is saved without asking, and the session shows it at once — Home, the tile, the notification (`VpnSession.profileRenamed`). Both come from one watch of the connection's profile (`watchConnectionProfile`, in `VpnRuntime`), which reads the profiles only while a connection exists: a deleted profile's credentials are not used again — its connection's engine stops, blocked once connected, ended during a first connect (J11) — and a renamed one is shown by its new name; a failure reading them is logged and the read tried again — 1 s after the first failure in a row, doubling up to 30 s, starting over after a good read — so the watch never ends with the failure. Saving and the reconnect finish even if the form is left meanwhile (Back waits while saving). A reconnect is a switch: traffic is held while the new settings are checked, and if they fail it stays blocked (B6a) until Try again, another Save and reconnect, or Stop — a change of network retries only a failure that may pass by itself (ADR-0012 §6), not the sign-in or certificate failures an edit most often brings — and not the waiting and retrying of an outage, since the user has just chosen these settings. Before M9 such an edit took effect only at the next connect.
5. **Onboarding runs once, before anything can connect.** A1 (what ProxyFlow is and what the user needs: an HTTP proxy that allows CONNECT or a SOCKS5 proxy, its address, port and sign-in; ProxyFlow sells no proxies), A2 (how it works: what goes through the proxy, what is blocked (UDP, ping) and what usually fails (local devices: their TCP is sent to the proxy too, their discovery is UDP) — that blocked traffic is never sent around the proxy, what the provider can see, why Android asks about a VPN and that there is no VPN server) and, on Android 13+ when notifications are not allowed, A3 (the status notification; "Not now" works too). Finishing saves `onboarding_completed` (DataStore); if saving fails, the pages are left for this process and come back next time. The notification permission is asked only there and from Settings, never at Connect (the VPN works without it, ADR-0010 §10). How it works stays reachable from About.
6. **Settings holds what the user can change, and says what they can't.** Kill switch (unchanged from M8); Logs & privacy: "Keep logs for" 1 hour, 24 hours (default) or 7 days — a shorter one deletes older entries at once — and "Clear logs now" behind a confirmation, which then says the log was cleared, or that it couldn't be and stays as it was; App: status notifications as Android reports them (on resume), opening Android's notification settings for the app; theme (system, light, dark); Help; About & privacy. Two switches the M1 board drew are left out: **"Reconnect automatically"** — reconnecting with traffic held is part of failing closed (ADR-0012 §6, ADR-0013 §1), and turning it off would only make every outage a blocked connection the user must restart, with nothing gained; **"Record destinations"** — the log keeps no site names or addresses (`LogSanitizer` replaces them, ADR-0012), which is what the privacy policy promises; recording them would need its own review of the log, the export and the threat model (I-9), not a switch.
7. **About links the pages a user and a store reviewer look for.** How ProxyFlow works (A2's page), the privacy policy (what is kept on the phone, what is sent where — including the pre-flight and test target — and that ProxyFlow itself sends nothing to its developer, who has no servers; Google may show the developer the crash and freeze (ANR) reports a phone shares with it, with the phone's model, Android and app version and country or region), Help (getting started, what each failure means and what to try, certificates and TLS, the kill switches, feedback), and the open-source licences. "Learn more" on Home's certificate errors opens Help at its certificates topic. The pages are in the app, so they work without a network; `docs/m9/privacy-policy.md` carries the policy, made from the app's text, for the public URL Google Play needs (owner decision D9, new in M9: where it is published, and the support contact).
8. **Open-source notices are generated from what ships, and checked.** `scripts/licences.py` lists every library on the release runtime classpath with the licence its POM declares (or its parent POM's), and the Go modules linked into the engine as `go version -m` reads them from `libgojni.so` (the engine job's facts), with the Go toolchain itself. Only licences whose full text the app ships are accepted — Apache 2.0, Go's BSD 3-Clause with its copyright line, and gVisor's LICENSE file (Apache 2.0, with the MIT and BSD licences some of its files carry), each fetched from the project at the pinned version, and Protocol Buffers' LICENSE file (BSD 3-Clause, Google's copyright line) for the protobuf runtime DataStore repackages (`datastore-preferences-external-protobuf`, whose POM names BSD-3-Clause without its copyright holder: an override in the script, with its reason) — so a library under any other licence, one that declares none, or a Go module `docs/m4/dependency-review.md` has not reviewed fails the build instead of being guessed. The engine's own module, which gomobile links in from the checkout (the engine's facts list it, replaced by the checkout's directory), is ProxyFlow's code, not a notice; any other module built from a local directory fails, a replaced module is listed as what replaces it (`build-aar.sh` marks the replacement), and an override is applied only while the library's POM still declares the licence it was reviewed for. CI regenerates the list in every run and fails if it differs from the committed `open_source_licences.json`. The screen groups the libraries by licence and opens each text.
9. **The Quick Settings tile (B11).** On while ProxyFlow connects or a connection exists — connecting (a first connect too, while apps still use the normal network until the proxy is checked), connected, reconnecting, waiting for a network or blocked (blocked traffic is never shown as off) — and off once disconnected. Without a profile it is off and says "Add a proxy first", and a tap opens Home: Android delivers no tap to an unavailable tile, so it is never shown as one. A tap disconnects a connection that is still connected when the session gets to it (as Home's Disconnect; `disconnectIfConnected`, so a tap that crossed a failure never lets held traffic go) or connects the profile Home shows (as Home's Connect, which makes it the chosen one, ADR-0013 §3); anything that needs Android's consent screen or a confirmation — a connection being set up or held, blocked traffic — opens Home instead. The tap reads the profile first and the state after it, so it acts on the state as it is then. On a locked phone the tile names no profile and a tap asks to unlock first (`unlockAndRun`), so the VPN can't be turned off from the lock screen; since Android keeps showing a tile as last drawn — on the lock screen too — until it listens again, the tile is redrawn without a name each time it stops listening. A failure reading the profiles is logged and never ends the process the VPN runs in. Only the system UI can bind it (`BIND_QUICK_SETTINGS_TILE`, checked in the release manifest); a long press opens Home.
10. **Accessibility and layout are checked on every screen drawn.** Each screenshot test now also checks what TalkBack reaches: every control has a name it reads out and a touch target of at least 48 × 48 dp — its layout node, which includes the room Material's controls reserve around what they draw (an icon button draws 40 dp, a chip 32 dp). Section headings are headings to TalkBack, so it can move between them. Twelve screens are drawn again on a 320 dp-wide phone at Android's largest font size (200 %, set as Android sets it, so dialogs and sheets scale too), each scrolled to its main action — or showing it where it stays: a floating or bottom button, the top bar — which must then be on screen. Every screen is drawn in both themes; dialogs, sheets and menus in one. Material's extended floating button is named for TalkBack by its icon, not its text, so the icon carries the words; a sheet's drag handle gets a 48 dp target. Status is never colour alone (icon and words with it), and the contrast of the design tokens' colour pairs is checked in CI by `design/tools/check_contrast.py`.

## Alternatives considered

- **Keep "Test connection" unavailable until a later milestone**: M9 forbids placeholder functionality, and the engine has offered the check since M5.
- **Test with an HTTP request through the tunnel** (M1's plan for D6: one HTTPS request to a documented URL): it would send a request ProxyFlow does not need to send and widen what the privacy policy must disclose; opening the tunnel already proves the proxy signs in and reaches the internet. D6 stays open for the owner, and the target is one constant (`VpnSession.PREFLIGHT_TARGET`).
- **Test through the VPN, or start the VPN for a test**: it would change the phone's network for the length of a test, and the test of one profile would go through another while connected.
- **Keep results per test session only**: board C2 and J3 ask for the result on the profile, and a result that outlives an edit would describe settings that are gone — hence the rule in §2.
- **A picker that only changes the active profile and leaves the connection**: Home would show one proxy and the connection use another until the next connect — the inconsistency §4 removes. A confirmation in the picker as well: the sheet says what switching does before the tap, and switching sends nothing around a proxy; the profile list says nothing beforehand, so it asks.
- **Deciding the switch in the screens** (switch only if a connection runs, as each screen sees it): a screen's view of the connection can be a moment old, so a Stop just sent could be undone by a pick; the session decides, in order.
- **Asking only when a switch would hold traffic**, switching silently during a first connect: the screens decide on what they last saw, and a first connect that finishes in the moment before the session acts would turn that silent switch into one that holds traffic, unasked. Asking whenever a connection runs, in words that follow its state while the question is open, leaves only the moment between the tap that confirms and the session acting on it — after the choice is saved, or, for D9, after the profile is; a first connect that finishes in it makes the switch one that holds traffic, as any switch once connected does — never one that sends anything around a proxy.
- **Generate the notices with Google's OSS licenses plugin**: it adds a Play services library to the app and reads only Maven metadata; the Go engine's modules would still need their own notices. A hand-written list would go stale with the next dependency update.
- **A tile that disconnects whatever the state**: leaving a held state sends apps to the normal network, which Home confirms first (docs/m1/04 §7); the tile opens Home there instead.
- **An accessibility scanner library (ATF) in the tests**: another test dependency to review; the two checks that matter for these screens — a spoken name and the touch target — are a few lines on Compose's semantics tree. Contrast is checked on the design tokens.

## Consequences

- The profiles database is at version 3; a phone with version 1 or 2 migrates on first launch, keeping every profile and credential (tested).
- A test from the form or the list contacts the proxy and the pre-flight target, which the privacy policy states; nothing else in M9 adds network traffic.
- "Use this proxy" now asks first whenever a connection runs on another saved profile, then switches as B8 does; saving changes to the connection's own profile reconnects with them, after D9.
- Every dependency update now also needs its licence to be one the app ships the text of, or a reviewed addition to `scripts/licences.py`. Every library the release build ships is under Apache 2.0 except DataStore's repackaged protobuf (BSD 3-Clause), besides the engine's Go modules.
- The tile's state on the lock screen names no profile; the profile's name appears once the phone is unlocked and the panel is opened again.
- `ConnectionController`'s intentions added in M9 (`reconnect`, `switchIfConnected`, `disconnectIfConnected`) do nothing by default, as its earlier optional ones do, so each screen's test double implements only what that screen sends. The app's one real controller, `VpnConnectionController`, overrides every one of them and passes it to the session; a new intention needs that override too, which review checks, since a missing one would compile and do nothing.
