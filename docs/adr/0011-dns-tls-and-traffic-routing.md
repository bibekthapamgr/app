# ADR-0011 — DNS, TLS and traffic routing on devices (M6)

**Status:** Accepted 2026-11-01 (technical decisions delegated by the owner, "Timi nai decide gara"; implemented in M6) · **Date:** 2026-11-01

## Context

ADR-0001 to ADR-0005 fixed what the engine carries (TCP), what it answers itself (DNS) and what it refuses (UDP, ICMP), and M4 and M5 built it: the engine on the phone's VPN interface, Connected only once Android routes apps into it. M6 asks for routing that is predictable and shown to be so: a traffic matrix for TCP, DNS, UDP, ICMP and IPv6; proxy-side name resolution; no silent fallback to direct DNS or direct connections; explicit behaviour for unsupported traffic; IPv4 and IPv6 tested; TLS to the proxy told apart from HTTPS to sites in the UI and the documentation; diagnostics for TLS failures, DNS failures, unsupported flows and proxy timeouts; and verification with packet captures and controlled DNS and proxy servers.

Looking at the engine against that list found three gaps:

1. **DNS over TCP.** UDP port 53 to any address is answered on the phone (ADR-0003), but TCP port 53 was an ordinary TCP flow: sent to the proxy as an address, so a lookup over TCP was resolved by a public resolver behind the proxy, and the app then connected by address — the proxy saw addresses, not names. To the VPN's own DNS server (198.18.0.2) it was worse: an address in the placeholder range with no name, refused as `STALE_DNS_MAPPING`.
2. **The engine's own addresses.** Android's opportunistic DNS-over-TLS probe goes to the VPN's DNS server on port 853 whenever Private DNS is on "Automatic" (the default). It was refused (correct) but counted as a stale mapping, which the diagnostics would have shown as a failure of the user's apps.
3. **Diagnostics.** The engine counted failures by error code, but could not tell a timeout of the proxy from a refusal, nor a failure for a name (often a lookup the proxy could not do) from one for an address.

## Decision

1. **DNS over TCP port 53 is answered on the phone**, to any address, like DNS over UDP: same placeholders, same record handling (ADR-0003 points 2–4), RFC 7766 framing, several queries per connection, closed when idle (2 s). Nothing is forwarded. DNS-over-TCP connections have their own limit (32 at once, `MaxDNSOverTCP`), apart from the DNS-over-UDP sockets' 256, so connections an app keeps open cannot take the slots every app's lookups need. This amends ADR-0003 point 6 for plain DNS over TCP; DNS over TLS (853) and over HTTPS chosen by an app stay ordinary TCP through the proxy (they are encrypted; ProxyFlow cannot and does not answer them).
2. **TCP to ProxyFlow's own addresses** other than DNS is refused on the phone with a RST and counted apart (`local_refused`), not as a failure of an app's connection: the reserved start of the placeholder range (198.18.0.0–198.18.0.255, with the DNS server's 198.18.0.2) and the TUN's IPv6 address (the engine's `LocalAddrs`). Android's opportunistic DNS-over-TLS probe to 198.18.0.2:853 is the case that occurs; Android then falls back to plain DNS, which ProxyFlow answers. (The TUN's own addresses, 198.18.0.1 and `fd00:66::1`, are local to the phone: its kernel answers connections to them without the engine; the engine refuses them too should one arrive.)
3. **No fallback, anywhere** (unchanged, now shown on devices): a failure to reach, sign in to, verify or get an answer from the proxy ends that connection with a RST, a refused name ends at the proxy, UDP gets "port unreachable", a ping gets nothing. ProxyFlow never retries a connection directly, never resolves a destination itself, and never retries TLS without TLS. The only name it looks up outside the proxy is the proxy's own (ADR-0003 point 5), and a failure there is `PROXY_DNS_FAILED`, never retried through another resolver.
4. **IPv6**: TCP to an IPv6 address goes to the proxy by address (SOCKS5 ATYP 4, `CONNECT [addr]:port`); names are answered with IPv4 placeholders only (AAAA, HTTPS and SVCB get no records), so a name with only IPv6 addresses still reaches the proxy as a name and the proxy reaches it over IPv6 if it can; UDP over IPv6 is refused and ICMPv6 echo dropped like IPv4. The VPN routes `::/0` with a ULA address (`fd00:66::1`), so apps see IPv6 as available even where the uplink has none; any IPv6 they use goes through the proxy or fails.
5. **TLS to the proxy** (ADR-0005, unchanged): TLS 1.2 or newer, the leaf's name and dates checked by the engine, the chain by the platform's trust manager (system CAs, Android's distrust rules, the app's network security config). There is no setting, prompt or button to accept a certificate anyway, and no plaintext retry. Private CAs and user-installed CAs are not trusted in V1. As with any TLS client, a resumed session is not a new certificate check: a proxy that changes its certificate but keeps accepting its old session tickets is accepted on those tickets until they expire (the chain verified when the session began is checked again, not the new one).
6. **A test-only trust seam.** The device tests must show TLS to the proxy working end to end, which needs a certificate the phone trusts; no public CA issues one for a lab proxy. `AppContainer`, `VpnRuntime` and `ProxyTunnelEngine` take the trust manager for TLS proxies as a constructor parameter, the platform's by default. Only the instrumentation passes another (`E2eTestRunner` → `TestProxyFlowApplication` → `TestTrust`): the platform's own `TrustManagerFactory` trust manager with the CI run's CA as its one anchor — the same implementation and checks, other anchors. The app as installed never sets it (`ProxyFlowApplication` uses the default), and one device test (`theAppAsShippedTrustsNoPrivateCa`) runs with the seam handing out the very trust manager the app uses by default (`AndroidEnginePlatform.systemTrustManager()`, no lab anchor) and shows the run's CA refused (`TLS_UNTRUSTED`). Rejected alternatives: a debug network security config with `debug-overrides` (would make every debug build trust a CA whose key lives in the repository), installing the CA in the system store (needs root and a writable system image, not available on every API level in CI).
7. **Diagnostics.** The engine counts proxy timeouts (`proxy_timeouts`: connecting to the proxy or its handshake took too long, `adapters.IsTimeout`) and failures of flows to names (`hostname_failures`). Home shows, while connected, what went through the proxy (connections; the different names apps looked up during this connection, left to the proxy to resolve, counted once each by the engine as `dns_names`) and four kinds of problems: **TLS to the proxy** (failures and which check failed), **DNS** (connections to names the proxy could not resolve or reach, failed lookups of the proxy's own name, lookups dropped, stale placeholders; query types ProxyFlow does not answer by design are shown there but never count as failures), **unsupported traffic** (UDP packets refused, with the ports refused most; pings dropped) and **proxy timeouts**, plus the last failed connection's code. The DNS row is a heuristic: a proxy reports a name it cannot resolve as it reports a host that is down, and some proxies only as a general failure, which then shows only as the last problem. Counts only: no destination, name or address appears, whatever the "Record destinations" setting. They are read from the engine once a second only while Home is shown. Connect-time failures keep their own screens (B6b) with the catalogue's code-specific texts.
8. **Copy.** TLS is always "TLS to proxy" (chips, form, Home, About), never plain "encrypted"/"not encrypted", and wherever it is explained the text adds that HTTPS sites stay encrypted end to end and that ProxyFlow never decrypts them. No string may claim universal coverage ("all traffic", "every app", "full VPN"), anonymity or hiding identity, blanket security ("100 %", "military-grade", "protection"), or support for UDP, games or calls; About says what does not go through the proxy and that ProxyFlow does not make the user anonymous. `CopyClaimsTest` enforces this over every string of every module and language.
9. **Verification lab** (CI): real Dante and Squid with sign-in, resolving names only with their own DNS server (dnsmasq, logging); stunnel TLS fronts with certificates from a CA made for each run (valid, wrong name, expired, untrusted CA); a gate the tests break while connected (refuse, hang, swap the certificate); the phone's uplink DNS server (the emulator's `-dns-server`, logging); destinations by name, by IPv4 address, by IPv6 address, by an IPv6-only name and on the LAN address; an HTTPS site; UDP sinks. The device tests run their traffic from the shell user (whom the VPN covers) with a Java client started by `app_process`; `scripts/m6_evidence.py` checks the lab's logs and the packet captures of the phone's uplink, including, for the periods ProxyFlow was connected (each period but its first and last 2 s; each capture lined up with logcat by the phone's own connections to its proxy; a capture that cannot be lined up fails the run), that anything else that left the phone on its own network is accounted for: its proxy, its network's resolver, Android's network and time checks, or apps Android lets leave a VPN, named by the owner of the socket with that connection's own ends (a system uid, or an app granted a network bypass permission such as Google Play services) and reported; anything the shell, ProxyFlow or any other app owned fails the run, and what no sample named is put down to such apps only when Android's own view of ProxyFlow's VPN routed every uid but ProxyFlow's into it and ProxyFlow's own sockets reached nothing but its proxies (and the gate's control port the tests use), over IPv4 or IPv6.

## Alternatives considered

- **Forward DNS over TCP through the proxy** (the old behaviour): needs a proxy that allows port 53, resolves at a public resolver instead of the proxy, and gives the proxy addresses instead of names — the problems ADR-0003 rejected for UDP.
- **Answer DNS over TCP only on the VPN's own DNS server address**: an app with a hard-coded resolver over TCP would still bypass proxy-side resolution; UDP/53 is already intercepted for every address, so TCP follows the same rule.
- **Show diagnostics in the Logs screen only**: Logs, with retention and filters, are M7; the four kinds of problems M6 asks for belong where the user looks while connected. M7 builds on the same counters.
- **Distinguish a slow destination from a hung proxy for SOCKS5** (a timeout after the greeting succeeded): possible, but for HTTP CONNECT the two cannot be told apart, and the user-facing meaning is the same ("your proxy didn't open the connection in time"). Kept as one category; M7's escalation rule uses the existing proxy-level codes.

## Consequences

- Every plain DNS query, UDP or TCP, to any server, gets ProxyFlow's answer, so names reach the proxy as names. An app that sends something other than DNS to TCP port 53 is not served (it would have been proxied before).
- With Android Private DNS in strict mode, the resolver's DNS-over-TLS connection is carried through the proxy like any TCP (by name, resolved by ProxyFlow's placeholder); apps then connect by address, still through the proxy, and the proxy sees addresses. Not automated in CI: it needs a DoT server trusted by the system store (docs/m6/routing-and-limitations.md §4).
- The trust seam is a constructor parameter in shipped code. It has no runtime source (no setting, intent, file or network input), its default is the platform's trust manager, and a device test proves the shipped default refuses the lab's CA.
- Home's Connected screen is longer: the routing summary and the diagnostics card scroll below the timer.
- Android lets privileged system apps bypass a VPN. The evidence found Google Play services doing so on the Android 15 image over Wi-Fi (connections to ports 5228, its push messages, and 443, a few seconds into connected periods), and connections of the same kind once on Android 16 that no socket sample named (seen only in the emulator's capture, which may have been lined up about a second wrong). It reports what system uids and apps with a network bypass permission own, fails on any other owner, and puts what no sample named down to such apps only when Android's own view of the VPN routed every uid but ProxyFlow's into it. The limitation is in the routing doc §4 and in About.
